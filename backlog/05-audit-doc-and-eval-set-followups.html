Task — part A: the audit doc

  1. MIGRATION_AUDIT.md is a detailed, valuable session log — but it's sitting untracked in the repo root, which doesn't match this project's own documented convention of not leaving completed/stale narrative docs lying around (see CLAUDE.md's own history: commit 671621c deliberately deleted a stale "Open items" section rather than let it accumulate).
  2. Pick one: (a) fold anything still load-bearing into CLAUDE.md or these tickets, then delete it; (b) move it to a docs/history/ or similar archive location and commit it there deliberately; (c) commit it as-is at the repo root if the team wants a permanent record of this specific audit. Any of these is fine — leaving it perpetually untracked is the one option that isn't.

Task — part B: acceptable[] coverage

  1. Only 133 of 312 authored eval rows currently carry an acceptable[] synonym list, meaning lenient Recall@1 equals strict Recall@1 on the other 179 — the synonym-tie correction is partial, not applied uniformly.
  2. eval/audit/acceptable-recommendations.tsv already has candidate recommendations sitting unresolved (per CLAUDE.md §"Known limitation of v1") — start there rather than re-deriving from scratch.
  3. The eval set is frozen — this cannot be an in-place edit. Any change produces v2.jsonl, a fresh sha256 recorded the same way v1's was, and every committed reference run (eval/runs/baseline.json etc.) needs re-generating against the new set before it's trustworthy again.

Prerequisite knowledge

  • This is explicitly not urgent: CLAUDE.md already labels the partial acceptable[] coverage "deliberate MVP scope, not a bug." Don't let this ticket imply otherwise — it's here so it doesn't get forgotten, not because it's blocking anything.
  • Before starting part B, re-read CLAUDE.md §"The eval set — frozen, never regenerated in place" in full. The freeze discipline is the single thing that keeps every headline number in this repo trustworthy over time; getting the versioning wrong here undermines every ticket above it.

Learnings

✓

A repo's own documented conventions are a legitimate audit signal. This project explicitly prefers deleting completed TODO-style docs over accumulating them — that's not a generic best practice being imported from outside, it's this codebase's own established pattern, visible in its git history. Worth checking for on any project before deciding whether a working doc should stay.

!

"Low priority" and "no opinion on the answer" are different things. This ticket doesn't recommend which of the three audit-doc options to take — that's a genuine team call (permanent record vs. archive vs. fold-and-delete) — but it does insist one of them gets picked rather than the file quietly living in an untracked limbo indefinitely.
