Rerank the gloss shortlist with a cross-encoder

✓ Done
In plain terms

Search almost finds the right word, then puts it 8th instead of 1st. We tried a second model to fix the order. It made things worse.

Was — the right answer is somewhere in the top 100 for about 3 searches in 4 (77.0%), but shown first for only 1 in 4 (24.0%).

Did — added a second, slower model that re-reads the best 10–100 candidates and re-sorts them (reranking), and measured it offline against the frozen test set.

Result — done 2026-08-28, and negative. Every configuration scored below doing nothing. Nothing shipped; users saw no change. The gap it was aiming at is still there and still unclaimed.

Outcome: null result under the pre-committed rule — RD-13 stays blocked by its own gate Touched: scripts/eval.ts, scripts/lib/reranker.ts (new), scripts/lib/metrics.ts, scripts/probe-rerank-fusion.ts (new), lib/glossSearch.ts Cost: one day, no production exposure, no data migration Write-up: eval/METHODS.md §13

Retrieval finds the right answer far more often than it ranks it first. On the live gloss index the target is somewhere in the top 100 for 77.0% of queries but sits at rank 1 for only 24.0%. That gap — 53 points — is the largest block of addressable headroom this project has measured. This ticket tested whether an off-the-shelf cross-encoder could claim any of it. It cannot.

Result — done 2026-08-28

Three arms of ms-marco-MiniLM cross-encoders, shortlist depth swept 10/25/50/100, scored against the frozen set through the real retrieval path. Every arm at every depth scored below plain retrieval — best 24.4% against the baseline's 24.0%, with paired deltas of −3.8, −2.4 and −2.1 points of lenient Recall@1. Recall fell as the shortlist got deeper. The "<lemma>: <definition>" variant clawed back some ground only by driving echo from 14.5% to 21.4% — reintroducing the exact defect RD-02 removed.

The two halves of the ticket resolved opposite ways, and are recorded apart: the ceiling is confirmed and real, the available tool does not reach it. Nothing was served; /api/lookup was never touched.

What was measured

Lenient Recall@1, authored reachable slice (n=287), gloss index at probes=40. Retrieval alone scores 24.0% — the number to beat.

The depth sweep was free: a depth-D re-sort is a prefix of the depth-100 scores, so every column above comes out of one run's forward passes rather than four runs.

The ceiling — confirmed
77.0% reachable, 23.0% not
Lenient recall by depth: 24.0 → 51.9 → 72.5 → 77.0% at ranks 1/10/50/100. A perfect reranker over 50 candidates would reach 72.5%. The other 23.0% is never retrieved at any depth and no reranker of any size touches it — that slice belongs to RD-09/RD-14/RD-15.
The reranker — rejected
every arm negative
22 wins / 33 regressions, 23/30, 21/27. It is not inert — it moves ~50 of 287 queries per run and some wins are large and correct. It simply loses more than it gains, which is worse news than indifference: it has learned a real preference and the preference is wrong here.

Why it failed

The failure is legible in the scores, not just the aggregate. For the query "something you did wrong without ever meaning to do it" — target mistake, which retrieval already ranked first — the cross-encoder re-sorted it to 6th, promoting:

rankgloss it preferredword
1something done or paid in expiation of a wrongreparation
2a wrongful act that the actor had no right to domalpractice
6a wrong action attributable to bad judgment or ignorancemistake

It is scoring lexical relevance, and it is good at it — the gloss it promoted shares something, done and wrong with the query. These models are trained on MS MARCO, which pairs real search queries with web passages, so passage relevance is what transferred.

That is the wrong relation. A reverse-dictionary query is a description and a gloss is a definition; the two are related by paraphrase, not by shared terms. This is echo again — the same failure RD-02 removed from the index, relocated one stage later into the reranker. "More accurate" turns out to be a property of the data a model was trained on, not of the architecture, which is the assumption this ticket existed to test.

The fusion control — and why it is not a rescue

The obvious objection is that reranking replaced a good signal instead of adding to it. Tested with Reciprocal Rank Fusion, chosen because it has no free parameter to fit and consumes only ranks, so it cannot be flattered by two scores on different scales.

fused armdepth 102550100
L-6, gloss23.023.322.622.6
L-6, lemma + gloss24.725.425.125.1
L-12, gloss25.825.124.424.7

Fusion recovers the loss and edges past baseline — best cell 25.8%, +1.8 points. The project's pre-committed rule says a gain under ~6 points is a null result and is not to be acted on, and here that rule is doing real work: 25.8% is the maximum of 24 cells (3 arms × 2 orderings × 4 depths), picked after seeing them, on a 287-query single-register set. The bar exists so a post-hoc maximum cannot be written up as a win.

Recorded, not pursued. If a fine-tuned reranker is ever scoped, fusion is the combination rule to start from — and this table is its prior, not its result.

Task

  1. Score the gloss, not the word. Done — the primary arm scores (query, gloss). The "<lemma>: <definition>" variant was measured rather than assumed, and it behaved exactly as Phase E predicted: better recall, bought with echo.
  2. Sweep the shortlist depth and record it in code. Done — 10/25/50/100, recorded in scripts/lib/reranker.ts in the shape GLOSS_PROBES uses. No depth constant was defined, deliberately: a named production depth would imply a shipped stage.
  3. Raise probes alongside the depth. Not needed, and the reason is the finding itself. Deeper shortlists made results worse, so widening the scan to feed a deeper one had nothing to buy. The k=10 decision was never inherited — it was made irrelevant.
  4. Extend the harness; do not write a one-off scorer. Done — a stage over the existing ranked array. lib/glossSearch.ts gained searchGlossSynsets() so synsets survive to the harness, and searchGloss() composes over it with byte-identical SQL.
  5. Persist the shortlist. Done, and it paid for itself within the hour: the fusion control was answered from a file read instead of another 40,500 forward passes.
  6. Start off-the-shelf. Done — two models, no fine-tuning. Cost a day to find out, exactly as scoped.
  7. Gate on paired McNemar against prod_gloss_shipped. Done — and a gap was found: --compare only ever tested strict rank-1, while the decision rule resolves on lenient. Fixed; both are now reported.
  8. Report strict and lenient separately, and echo alongside both. Done — and echo is what caught the lemma-gloss variant.

Learnings

!

A diagnostic does not survive the change it motivated. "A reranker has nothing to reorder" was correctly measured, correctly reasoned, and quietly became false the moment RD-02 shipped — because it was a fact about the lemma index wearing the costume of a fact about reranking. It then sat in CLAUDE.md as an argument against the highest-headroom item in the backlog. When a fix lands, re-check the findings that were true because of the thing you fixed.

✓

The number that justifies this ticket was already in the repo, uncomputed. --rank-depth defaults to 100 and deep mode is on by default, so every committed run since the cutover carried its own reranker ceiling in its per-query rank field. No new experiment was needed — only reading the artifact at a depth nobody had asked it about.

!

"More accurate model" is a claim about training data, not architecture. A cross-encoder genuinely does read the pair together, and that genuinely is more expressive. It bought nothing here, because MS MARCO taught it web-passage relevance and this task needs description-to-definition paraphrase. The architecture was never the missing piece. Reading the model's actual ranked output on one query explained the whole aggregate — and cost a minute.

✓

A big measured ceiling is not a plan. 53 points of headroom made this a P0, and the headroom is real — but headroom says what is possible, never what is available. The two got recorded separately here precisely so the next person does not read "rejected" as "the opportunity is gone", or the 77.0% as a promise.

!

The decision rule earned its keep on a result it was not written for. Rank fusion hit +1.8 points and it was tempting. It was also the maximum of 24 cells chosen after seeing all 24, on 287 queries. The ~6-point bar was pre-committed in 2026-08-19 against a representation change and it disposed of this cleanly a year of context later — which is the entire argument for pre-committing thresholds rather than judging deltas as they arrive.

✓

Splitting build from cut-over is what made a negative result cheap. RD-12 measured, RD-13 would have served, and RD-13 was gated on this number existing. The gate held: a day spent, nothing deployed, no rollback needed, no user affected. Same shape as RD-01/RD-02, and it is worth just as much when the answer is no.

!

The tooling could not compute the number the decision rule resolves on. METHODS §9a was amended to lenient Recall@1 in August; --compare ran its paired test on strict rank-1 the whole time, and over all 405 rows rather than the 287-row headline slice. Every paired verdict since had been read off the wrong metric on the wrong denominator. Found only because this ticket's acceptance criteria named both explicitly. A pre-registered metric needs a test that it is actually the one being computed.

!

Two implementations only protect you if something compares them. scripts/report.ts had computed the paired test correctly all along; eval.ts --compare had not. They disagreed for months. The wrong one is the one a person runs at a terminal and pastes into a commit message — so its numbers reached CLAUDE.md, README, ARCHITECTURE and RD-02's own ticket ("64 wins / 17 regressions"; the truth is 55 / 15) while the generated report sat beside them saying otherwise. The redundancy was real and bought nothing until someone asked why a delta disagreed with a figure already written down.

✓

Persisting the shortlist turned a follow-up question into a file read. "Does fusing the two orders help?" arrived after the runs finished. Because the candidates and their scores were on disk, it cost one script and no GPU — instead of re-running 405 embeddings and 40,500 forward passes. The cheapest time to store an intermediate is while you already have it.

!

Neon auto-suspends, and the harness had no defence. The first query of a run pays several seconds of compute wake-up: it wrecks the latency p50 exactly as an ONNX cold start would, and it can exceed Prisma's 2-second transaction maxWait and abort a 405-query run before a single row is scored. The embedder had been warmed before timing since the harness was built; the database had not. It is now.

Acceptance criteria

  • Reranker implemented as a stage over the existing harness retrieval path, not a second retrieval implementation — searchGlossSynsets() was extracted from searchGloss(), which now composes over it.
  • Verified behaviour-preserving: a depth-1 rerank (rerank_null) reproduces prod_gloss_shipped with 0 discordant pairs and every headline digit identical.
  • Cross-encoder scores (query, gloss); the lemma-bearing variant measured, not assumed — and it cost +6.9 points of echo.
  • Shortlist depth swept (10/25/50/100) and recorded in code with its measurements, following GLOSS_PROBES.
  • probes re-tuning made moot rather than inherited: deeper shortlists scored worse, so there was no deeper scan worth feeding.
  • Run artifacts persist the full shortlist — compact form in the run JSON, gloss text in a .shortlist.jsonl sidecar.
  • Off-the-shelf cross-encoders measured before any fine-tuning was scoped — two of them, and fine-tuning is now a decision to make against these numbers.
  • Paired McNemar vs. prod_gloss_shipped reporting strict R@1, lenient R@1, R@10, MRR@10 and echo — and --compare gained the lenient test it had been missing, on the headline slice it should always have used.
  • Result recorded following CLAUDE.md's "Headline results" convention, stating the 77.0% ceiling and the 23.0% it cannot reach. Full write-up in eval/METHODS.md §13.
