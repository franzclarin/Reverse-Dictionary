One image for the whole project

✓ Done P2 · tooling
In plain terms

Today — the project ran in exactly two places: this laptop, set up by hand, and Vercel. There was a container, but it covered only the notebook half of lab/ — not the app, not the model, not the training environment. Handing the whole thing to someone else meant a page of instructions and hoping.

Done — one Dockerfile that carries everything: the app, the 87 MB model it serves, and both Python environments. docker compose up web gives you the running site; docker compose up lab gives you the notebooks.

Why it matters — reproducibility, mostly. But it also found a real defect that only a linux build could find: the training environment had been quietly resolving a GPU build of PyTorch it can never run.

Status: done 2026-08-31 — image builds, /api/lookup answers from it, both kernels serve Touches: new Dockerfile, compose.yaml, .dockerignore, DOCKER.md, plus a lockfile pin in training/ Does not touch: next.config.js, package.json, lib/, app/, vercel.json — the serving path and the deploy path are unchanged Risk carried: the container is CPU-only, and its torch build differs from the host's

The repo already had a container. It covered the smallest surface and skipped the one that ships.

The defect it found

training/uv.lock resolved torch to the CUDA build on linux — nvidia-cublas, nvidia-cudnn, nvidia-nccl, triton and fourteen more. Roughly 2.9 GB of libraries that can never execute, because Docker on macOS has no GPU at all, let alone an NVIDIA one.

Nothing was wrong on the host, and nothing ever would have been: the lock was correct for darwin and had simply never been resolved for linux. lab/ hit the identical trap when it was containerised and fixed it with a platform-scoped index pin; training/ got the same pin, verbatim:

[tool.uv.sources]
torch = [{ index = "pytorch-cpu", marker = "sys_platform == 'linux'" }]
after re-locking
nvidia references in training/uv.lock18 → 0

container (linux) torch2.13.0+cpu

Verified by extracting every name/version pair from the lockfile before and after and diffing them, rather than by reading the summary uv printed. One lockfile still serves both surfaces.

Decisions

No database in the compose file

The obvious shape — app plus a pgvector service — is wrong here. GlossEmbedding is 693,325 rows and is not in the repo; a local Postgres would come up with the schema and zero rows, so /api/lookup would return an empty list and every number measured against it would be fiction. Rebuilding the index is an embedding job over 693k senses, not a seed script. The container connects to the same Neon database local dev does, and inherits the same cold-start behaviour (61 ms warm, 2,678 ms cold).

No output: 'standalone'

The conventional Next.js Docker recipe would have meant editing next.config.js — the file that carries RD-11's outputFileTracingIncludes for the model and the counterweight excludes for onnxruntime-node's per-platform binaries. Slimming the image is not worth touching the config the Vercel build depends on, in a repo where the deploy path is already documented as fragile. Copying the built app wholesale costs layer size and nothing else.

Two Python environments, not one

lab/ deliberately does not import training/rdlib, because rdlib already implements the scoring, retrieval, echo metric and paired significance test that the from-scratch rebuild exists to reimplement. Merging them into one venv would have made that rule a matter of etiquette. /opt/venv-training and /opt/venv-lab make it a property of the filesystem. Both kernels are registered system-wide, so one JupyterLab server still offers both.

Prerequisite knowledge

  • ENV PATH does not survive a login shell. bash -l re-sources /etc/profile and resets PATH, so docker compose exec … bash -l silently gets the base image's python and fails to import torch. /etc/profile.d/10-venv.sh re-prepends ${RD_VENV}. lab/ found this; this image inherits the fix and the reason.
  • Kernel names are load-bearing. The committed notebooks declare reverse-dictionary and reverse-dictionary-lab; an image that registers only python3 prompts for a kernel on every open.
  • The build needs network, because scripts/fetch-model.mjs runs inside it. That script verifies exact byte sizes, so a truncated download or an HTML error page served with a 200 fails the build — which is the correct outcome given allowRemoteModels = false.
  • The container is CPU-only. Docker on macOS runs a Linux VM with no Metal passthrough. Do real training on the host; use the image for portability.

Learnings

!

A lockfile is only checked for the platforms it has been built on. training/uv.lock had been correct and complete for a year of macOS use while carrying 2.9 GB of CUDA for a platform nobody had ever resolved it against. The container did not cause that problem; it was the first thing to ask. Same shape as the stale 512 MB storage ceiling RD-17 corrected and the missing zip RD-22 found — a claim nobody had re-checked, because nothing forced the question.

✓

The second container was cheaper than the first because the first had already been debugged. Three of this image's non-obvious decisions — the CPU index pin, /etc/profile.d, the kernel names — are lab/'s learnings applied without re-discovering them. Writing those down as commit-message prose, rather than as a fixed Dockerfile alone, is what made them portable.

✓

The parity gate travelled, and told the truth about the difference. RD-22's nine checks pass inside the container, including the PyTorch-vs-served-ONNX comparison — but at max abs diff 1.90e-07 against the host's 1.6e-07, because the encoder is running on a different torch build. Both are float32 rounding and both pass. It is a small, concrete instance of the rule the README already states: the container is a reproducible environment, not a bit-identical one.

✓

The right shape for this compose file has one service missing. Adding a pgvector service would have looked more complete and produced a container that returns nothing for every query. The index is 693,325 rows of derived data and belongs where it is; a database service here would have been a convincing prop.

Acceptance criteria

  • One image builds and carries the app, the model, and both Python environments
  • /api/lookup answers correctly from the container, against Neon
  • The model is served from inside the image, provably without network
  • No CUDA in the linux resolution, and no version drift on the host
  • Both Jupyter kernels present under the names the committed notebooks declare
  • The frozen eval set is read-only across the mount
  • No change to next.config.js, the serving path, or the Vercel deploy path
