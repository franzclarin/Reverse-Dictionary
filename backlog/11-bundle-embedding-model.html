Ship the embedding model in the function bundle instead of downloading it per cold start

✓ Done
In plain terms

The first search after a quiet spell took 43 seconds. It now takes a fifteenth of a second.

Was — the server code that answers a search shuts down when unused (a cold start). On waking, it re-downloaded the 86MB model from a public CDN before it could answer anything.

Did — shipped the model inside the deployed code, so waking up reads it off local disk instead.

Result — done 2026-08-27. 43,050ms → 64ms, with the model's output unchanged bit for bit. The measurement is what mattered: the wait turned out to be 99.8% network and 0.2% computing, which ruled out both a smaller model and a keep-warm timer.

Touches: lib/embedder.ts, next.config.js, scripts/fetch-model.mjs Risk: deploy-time — function bundle size, build-step network Est: S — one build step + one env block Orthogonal to: RD-03 (no dependency or pipeline change)

Every cold start of /api/lookup downloaded the 86MB ONNX model from the Hugging Face CDN before it could answer anything. The fix is not to make the model smaller or the load faster — it is to stop doing the download at request time at all.

Result — done 2026-08-27

The model is fetched during the build and traced into the function bundle; lib/embedder.ts loads it from local disk with remote fetching disabled. Measured through lib/embedder.ts on the same machine, same probe strings: 43,050ms → 64ms to load. Query vectors are bit-identical across all probes (3 × 384 dims), and eval:prod reproduces the committed reference run with 0 of 405 queries differing in rank or top-k — retrieval is provably untouched. Traced function bundle came in at 151.6MB after also dropping the non-linux ONNX binaries.

The measurement this ticket rests on

Cold start was timed directly, splitting the CDN download from the ONNX session init, because the two have wildly different fixes and it was never obvious which dominated:

phasetimewhat it is
Cold: download + init38,848 msfetching 90,374,450 bytes from the HF CDN, then initialising
Warm cache: init only69 msthe same model, already on disk
First embed after load3–6 msthe actual inference

The cold start was 99.8% network and 0.2% compute. That single ratio decides the whole ticket: nothing about the model, the runtime, or the inference was worth optimising, because none of them were the cost.

Same model, same vectors — only the source of the bytes changed

How it works — current implementation vs. goal

The work didn't get faster — it moved from per-request to per-deploy
Before
Fetch per cold start
allowLocalModels = false, cacheDir = "/tmp/transformers_cache". Every new instance re-downloaded 86.2MB. maxDuration = 60 existed to survive it.
After
Fetch per deploy
allowLocalModels = true, allowRemoteModels = false, localModelPath = <cwd>/models. The build downloads it once; the function only ever reads local disk.

Task

  1. Add scripts/fetch-model.mjs — idempotent, byte-size-verified download of the 4 required files. Done. Plain .mjs because it runs ahead of next build and must not depend on tsx resolving.
  2. Wire it into build, not postinstall. Done — "build": "npm run fetch-model && next build". Vercel caches node_modules and may skip postinstall on a cache hit, and a network call in postinstall would break npm install whenever HF is down.
  3. Point lib/embedder.ts at the local directory and disable remote loading. Done.
  4. Trace models/** into the function via outputFileTracingIncludes. Done — verified in route.js.nft.json, 4/4 files present.
  5. Gitignore /models/. Done — the 86MB artifact is regenerable and never enters git.

Prerequisite knowledge

There is no quantized model — don't go looking for one

The obvious first instinct is to shrink the download with an int8 model. onnx/model_quantized.onnx does not exist in franzclarin/ReverseDictionary — HF returns a 15-byte Entry not found body. quantized: false in lib/embedder.ts is not a tuning choice, it is the only artifact there is. Producing one is a real option but a separate ticket: it changes the query vectors that all 117,791 GlossEmbedding rows are matched against, so it cannot ship without a full eval:prod run behind it.

Cron warming does not work for this shape of problem

The other obvious instinct — ping the endpoint every few minutes to keep it warm. The Transformers.js cache is written to /tmp, which is per instance. A warm ping keeps exactly one instance warm while every instance Vercel scales up still pays the full 38.8s. It converts a reliable problem into an intermittent one, which is worse to diagnose and no better to experience.

The four files, and only those four

The HF repo has 14 files. The feature-extraction pipeline requests exactly four: config.json, tokenizer.json, tokenizer_config.json, onnx/model.onnx. The rest — including model.safetensors, which is the same weights in a format this path never reads — would be pure bundle weight. The sizes are pinned in FILES in the fetch script and double as the integrity check: a truncated download, an LFS pointer, or an HTML error page served with a 200 all fail the size assertion instead of shipping a corrupt model.

Learnings

✓

Measure the split before optimising the whole. "Cold start is slow" has at least three plausible fixes — smaller model, faster runtime, keep-warm — and the 99.8/0.2 split invalidated two of them instantly. Timing the download separately from the ONNX init took one script and decided the entire design. ARCHITECTURE.md had estimated "~20s"; the real number was ~39s and, more importantly, its composition was the actionable part.

!

env.localModelPath defaults relative to the Transformers.js module directory, NOT process.cwd() (@xenova/transformers/src/env.js:52-53). It resolves to somewhere inside node_modules, so a models/ directory at the repo root is invisible unless the path is set explicitly. This is the single most likely thing to get silently wrong, and with allowRemoteModels left at its default the symptom would not be an error — it would be a silent 39s download, i.e. no visible symptom at all.

!

The on-disk layout must mirror the HF repo id. Files go to <localModelPath>/franzclarin/ReverseDictionary/…, because the library joins localModelPath with the model id it was given. Flattening the org/name nesting produces a not-found that reads like a missing file rather than a misplaced one.

!

Adding 86MB to the bundle nearly doubled it — and most of the rest was dead weight for platforms Vercel never runs. The traced /api/lookup bundle measured 195.3MB, close enough to the legacy 250MB function limit to matter (on Fluid Compute's 5GB it is a non-issue, but that is a dashboard setting, not a guarantee in the repo). File tracing pulls in onnxruntime-node's binaries for every platform: 74.1MB traced, of which the macOS and Windows copies are 43.7MB that a linux function can never execute. Excluding them via outputFileTracingExcludes brought the bundle to 151.6MB. Excludes affect only the traced output, so local dev on macOS is unaffected.

!

This changes the eval toolchain, not just the route. Eight files import lib/embedder — scripts/eval.ts, scripts/lib/retrieval.ts, scripts/lib/embedModel.ts, scripts/build-gloss-index.ts, scripts/probe-margins.ts, scripts/probe-representation.ts, scripts/audit-vocab.ts, plus the route. With remote loading disabled they all need models/ on disk, so npm run eval fails on a fresh clone until npm run fetch-model has been run once. That is a deliberate trade for the production guarantee, and the thrown error names the command.

✓

Fail loudly was the right call, and it is only safe because the build verifies. allowRemoteModels = false means a file-tracing miss is a hard model SubsystemError rather than a silent regression to the slow path. That is only a responsible default because fetch-model.mjs asserts exact byte sizes and exits non-zero, so a deploy cannot ship without the model. Fail-loud without a build-time guarantee would just be a new outage mode.

✓

An error message that hardcodes its retry constant will lie to you. The thrown error read "after 3 attempt(s)" because it interpolated MAX_LOAD_ATTEMPTS rather than the real count — while the loop had correctly broken out after one attempt via isNetworkError(). It cost a few minutes of chasing a retry storm that never happened. Now reports attemptsMade. Worth remembering wherever a retry loop can exit early.

!

npm run eval:prod overwrites a committed reference run. The tag prod_gloss_shipped writes straight to eval/runs/prod_gloss_shipped.json, which is one of the four baselines deliberately un-ignored in .gitignore. Running the gate therefore dirties the very file it is being compared against. Here the retrieval results were per-query identical and only dbMs/embedMs changed, so the file was restored with git checkout rather than committing timing churn into a frozen baseline. Diff it before you commit it, and if the results genuinely changed, that is a finding to reckon with rather than a file to update.

✓

maxDuration = 60 was deliberately left alone. Its stated reason ("model cold-start needs up to ~20s") is now obsolete and the comment was corrected, but the value stays: it is a safety ceiling, not a target, and lowering it would only create a new failure mode — a slow Neon query turning into a 504 — in exchange for nothing. Vercel bills actual duration, not the limit.

Acceptance criteria

  • npm run fetch-model lands 4 files, onnx/model.onnx at exactly 90,374,450 bytes; a second run skips everything in ~50ms.
  • Model load through lib/embedder.ts drops from seconds to double-digit ms — measured 43,050ms → 64ms.
  • Query vectors are unchanged: 3 probe strings × 384 dims, bit-identical before and after.
  • With models/ removed, /api/lookup throws a model SubsystemError in ~10ms naming npm run fetch-model — not a slow success.
  • npx tsc --noEmit, npm run lint, and npm run build all pass, with the fetch step running as part of the build.
  • All 4 model files appear in .next/server/app/api/lookup/route.js.nft.json.
  • Traced function bundle stays well under the legacy 250MB limit — 151.6MB.
  • npm run eval:prod reproduces the committed reference eval/runs/prod_gloss_shipped.json per query, not merely in aggregate: 0 of 405 queries differ in top-k order or rank, and the only fields that changed anywhere in the file are dbMs/embedMs timing noise. Headline unchanged to the digit — authored reachable (n=287) lenient R@1 24.0%, strict 20.6%, R@10 49.8%, echo 14.5%.
  • On deploy: build log shows the fetch step, and a cold request on a fresh deployment returns in well under a second.
