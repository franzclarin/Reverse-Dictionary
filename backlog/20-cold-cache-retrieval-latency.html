Cold-cache retrieval latency after the index grew 5.9×

P2 · performance
In plain terms

Search got six times more to look through, and every number this project records says that cost nothing. Those numbers are all measured under conditions no real user experiences.

Today — the eval harness warms the database and then fires 405 queries back to back, so the index is in memory by the second query. A real visitor arrives alone, at a database that has been asleep, against an index that is now 1,295 MB instead of 213 MB.

Measured — once warm, a search scans in 61 ms, which is fine. Cold, the same query took 2,678 ms. The harness cannot see that difference by construction.

Do — measure what a first visitor actually waits, from production, and decide whether it needs fixing. It may not. But right now nobody knows, and the instrument that looks like it knows is pointed elsewhere.

Caused by: RD-17 — 117,791 rows → 693,325, index 213 MB → 1,295 MB Touches: measurement first; then possibly lib/glossSearch.ts (GLOSS_PROBES), the Neon compute setting, or nothing at all Risk of not doing it: a real regression in the one number users feel, invisible to every instrument the repo has Est: S to measure. The bigger index looks faster at every percentile. Both facts are true and they are not in conflict: ~450 ms of each figure is a laptop-to-Neon round trip (CLAUDE.md says so explicitly), and a 405-query sequential run keeps the working set hot throughout. The harness measures a warm index over a sustained burst. Production is a low-traffic app against an auto-suspending compute, so the cold path is the common case, not the tail.

This is not a defect in the harness. It is a question the harness was never built to answer, stated so the next person does not read p95 = 913 ms as an answer to it.

Size — S to measure
Production timings, not local ones
The route already returns timingMs and already logs by subsystem. What is missing is a reading taken from iad1, on a compute that has been idle, on the first request.
Impact — the one number users feel
Warm 61 ms is fine; cold is unmeasured
Warm scan roughly doubled (~29 ms → 61 ms), which is exactly what a 5.9× table at a finer partition predicts and is not a problem. The cold-page cost is what changed shape, and it is the case most visitors get.

Task

  1. Measure from production before changing anything. Local EXPLAIN ANALYZE establishes that a cold/warm gap exists and roughly how large; it says nothing about how often a real request lands on the cold side. Sample timingMs and the [lookup] logs from iad1, split by time since the previous request.
  2. Separate the three things inside a slow response. Neon compute wake-up (already known, already why searchGlossSynsets() waits 15 s for a transaction), index pages being read from storage, and the scan itself. They have different fixes and only the third is affected by probes.
  3. Re-read the probes sweep against a cold cache. probes = 100 was chosen on recall — it sits exactly on the exact-scan ceiling, and probes = 10 costs 3.8 points of R@10 for 0.3 points of R@1. If cold cost scales with probes as the table above suggests (498 ms → 2,678 ms), that trade deserves re-reading with a latency term in it. Do not quietly retune on latency alone — the recall sweep is recorded in GLOSS_PROBES and any change has to argue against it.
  4. Consider the levers in cost order. Keeping the compute warm; a larger Neon compute so more of the 1,295 MB stays resident; lowering probes; or accepting it. The last is a legitimate outcome for an app with no traffic and no SLA — but it should be a decision with a number behind it.
  5. If nothing changes, write down the measurement anyway. The value here is mostly in knowing.

Prerequisite knowledge

Neon auto-suspends, and this project has already been bitten

RD-18 found the first query after an idle period dying with P2028 because Prisma's 2-second transaction default is shorter than Neon's wake-up. The fix was to wait longer (maxWait: 15 s), which makes the request survive rather than fast. A bigger index makes the post-wake-up request slower still, because more has to be paged in before the first scan completes.

Why warm cost roughly doubled, and why that is the expected half

A probe scans about rows / lists candidates. Before: 40 probes over 115 lists across 117,791 rows ≈ 41,000 rows. Now: 100 probes over 833 lists across 693,325 rows ≈ 83,000 rows. Twice the work, and 61 ms of it — entirely unremarkable. The interesting change is not the arithmetic, it is that the resident set needed to serve a query grew with the table.

The numbers in this ticket, and their limits

Measured with EXPLAIN (ANALYZE) from a laptop against the live database, three queries × three rounds per setting. Warm medians are stable and trustworthy. The "cold" column is a maximum observed, not a distribution — it is evidence that a large cold cost exists, not a measurement of how large it typically is. Producing that distribution is step 1.

Learnings

!

A benchmark that warms up cannot measure a system that never does. The harness warms the database deliberately and correctly — without it, ONNX and Neon cold starts land on query #1 and destroy the percentiles it exists to report. That same warm-up makes it structurally blind to the cost a first visitor pays, and the blindness is invisible because the output is a plausible latency table. When a change makes the working set bigger, the benchmark's warm-up is doing more work for it than before, and the reported number improves for a reason that has nothing to do with users.

✓

"No measurable cost" is a claim about the thing that was measured. RD-17's regression test was about recall, and on recall it holds. Latency was checked with the same instrument and came back better, which was true and not the answer. Two different questions, one table.

Acceptance criteria

  • Production latency sampled from iad1, split by cold vs warm, with the share of requests landing cold recorded
  • The three components of a slow response — compute wake-up, page reads, scan — separated rather than reported as one figure
  • The probes choice re-read with a latency term, and either kept with a stated reason or changed with a recorded sweep that argues against the recall one
  • An explicit decision on the levers, including "accept it" as a legitimate outcome
  • CLAUDE.md's latency guidance updated to say what the harness's dbMs does and does not describe
