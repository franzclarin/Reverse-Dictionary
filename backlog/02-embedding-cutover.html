Shadow-validate, then cut /api/lookup over to the gloss index

✓ Done
Depends on: RD-01 (done 2026-08-26 — unblocked) Touches: app/api/lookup/route.ts, ShadowLookup Risk: production search behavior change Est: 1 day rollout + soak period before final decision

This is the actual fix for the app's core known problem: search results that share a word stem with the query ("rain" → "rainstorm") tend to outrank the word the user actually meant. Offline evaluation already answered whether this works — decisively. What's left is validating it against real traffic before flipping the switch, because the offline eval set is 287 hand-authored, single-register queries and production traffic is not.

Result — cut over 2026-08-27, measured on the live index

/api/lookup now searches GlossEmbedding via lib/glossSearch.ts. On the frozen set's authored reachable slice (n=287), against the real Neon table rather than a local cell: lenient R@1 10.1% → 24.0%, R@10 26.1% → 49.8%, echo 40.7% → 14.5%, with 64 wins / 17 regressions, p < 0.00001 paired. That is inside the +12.9–15.7pp band the offline cells predicted. One surprise: probes=10 was badly undertuned for this index — it scored 18.5%, and raising it to 40 recovered 5.5 points for roughly 20ms of scan (see the learning below). VocabEmbedding is untouched and still indexed; rollback is reverting one call.

How the gate was resolved — soak retired, not satisfied

Steps 1–2 are done: SHADOW_LOOKUP_ENABLED is flipped, deployed, and live on the production aliases (commit d217c99, on main). Step 3's soak never completed and cannot complete — the gate was written in units of live traffic ("a few hundred sampled queries across normal daily/weekly patterns") and this app has effectively no organic traffic, so the threshold is unreachable rather than merely distant. Waiting longer changes nothing. The gate has therefore been retired and the decision made on the offline evidence, which was always the stronger instrument (see step 3's reasoning below and the decision record at the bottom). The real-phrasing question the soak was standing in for is now tracked separately as RD-10.

Prerequisite knowledge

Why the offline numbers alone don't authorize a cutover

scripts/shadow-compare.ts's own header comment is explicit about this: it can report agreement rate between the old and new systems on live traffic, never accuracy, because no query text has ever been logged and there is no ground-truth label for a real user's query. The eval set's McNemar result (below) is the prior; shadow agreement is the live-traffic sanity check against that prior — not a replacement for it, and not a second independent accuracy measurement.

The offline result this is acting on

Learnings

✓

The fine-tune was never the lever. Fine-tuned vs. base model on the same lemma index: only +4.5pp, below the pre-committed 6pp bar for calling it real — a null result despite p=0.029. Swapping what's indexed beat retraining the model by roughly threefold. Don't let "should we fine-tune more" compete for priority against this.

✓

The approximate index and junk-vocabulary filtering are both confirmed non-issues. IVFFlat vs. exact scan costs ~0.3pp (p=1.0); --filter-junk moves recall 0.0pp. Neither is worth re-investigating as part of this rollout if the shadow numbers look off — look at the representation, not the index mechanics.

✓

Sense-familiarity tie-breaking is real but should be cited carefully. WordNet's own within-synset lemma order beats alphabetical by 2.5pp on identical vectors. It's a genuine effect (a person really is more likely to mean the common sense of a word), but it was also selected because it scored best on this eval set — mild benchmark-fitting. Keep both facts attached whenever this is cited.

✓

An index's probes tuning does not transfer to a differently-shaped index — and the cost of assuming it does was 5.5 points. The lemma index runs happily at probes=10, where the approximation costs ~0.3pp. The gloss index at the same setting lost 5.5 points of lenient R@1 (18.5% vs 24.0% at probes=40). lists=115 over 117,791 rows means each probe covers ~1,000 rows, and gloss vectors cluster far less cleanly than bare lemmas, so the answer often sits outside the 10 nearest lists. Measured sweep: 10 → 18.5%, 40 → 24.0%, 100 → 25.4% (the exact-scan ceiling), at roughly 8ms / 29ms / 166ms of scan. 40 is the knee. Re-measure this if the index is ever rebuilt with a different lists.

✓

The offline cells' absolute numbers did not transfer, exactly as the docs warned. cell_gloss_ft_synset scored 25.8% on a matched 20,287-word pool; production scores 24.0% against 117,791 live synsets. That is not a shortfall — a smaller candidate pool is an easier problem, and CLAUDE.md said the cell numbers were only valid for relative comparison before any of this was run. The thing that transferred, and the thing that mattered, was the direction and size of the gap between lemma and gloss.

!

The cutover is not a one-line query swap — budget for a real route change. VocabEmbedding returns k words directly (app/api/lookup/route.ts:65-72), but GlossEmbedding returns synsets (lib/shadowLookup.ts:38-46). The route has to over-fetch synsets, expand each one's lemmas[], dedupe across synsets (synonyms recur), and only then truncate to k. One detail worth not rediscovering the hard way: lemmas is stored in WordNet's own within-synset order (scripts/build-gloss-index.ts:45-46,57), which is the tie-break worth +2.5pp over alphabetical — preserve that array order, never sort it.

!

This app's search UX doesn't currently show a ranked list from a single call — check what "top-1" means for the current UI. The route returns a list of k results with similarity scores; the frontend's results page already renders the full list (not just a single top pick), so a gloss-index cutover changing which words appear in that list is user-visible immediately, not hidden behind a "top pick" abstraction. Sanity-check the results page rendering with gloss-index output before considering this done, not just the API contract.

Decision record

Recorded here rather than left as a template, following the project's convention of writing decisions down where the reasoning is still attached to them:

Shadow agreement rate: unmeasurable — n≈2 real rows over the soak window opened 2026-08-27. The app has effectively no organic traffic, so the sample never grew. Not a failure of the logging (the write path was verified end to end); a failure of the gate's premise.

Disagreements reviewed: 0 / 2 — a 2-row sample cannot support the qualitative review the gate called for, so none was attempted rather than over-reading noise.

Decision: cut over, on offline evidence. The gate existed to protect users from a regression; there are no users, so it protected nothing while deferring a measured +12.9pp lenient R@1 (53 wins / 16 regressions, p < 0.0001) and an echo-rate drop from 44.3% to 14.2%. That evidence is labelled — shadow data never could have been, since production traffic carries no ground truth. Deferring a strong labelled result for a weak unlabelled one that was never going to arrive is the wrong trade.

Rollback plan: revert the route's query to VocabEmbedding, which stays populated with its IVFFlat index intact and verified (RD-01, confirmed via EXPLAIN). No data migration is needed to roll back — it is a one-file revert.

Follow-up: RD-10 carries the real-phrasing measurement this gate was proxying for. ShadowLookup logging stays on; if traffic ever materialises the comparison becomes worth running retroactively.
