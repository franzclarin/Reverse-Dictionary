Shadow-validate, then cut /api/lookup over to the gloss index

P0 · sentence embeddings
Depends on: RD-01 (done 2026-08-26 — unblocked) Touches: app/api/lookup/route.ts, ShadowLookup Risk: production search behavior change Est: 1 day rollout + soak period before final decision

This is the actual fix for the app's core known problem: search results that share a word stem with the query ("rain" → "rainstorm") tend to outrank the word the user actually meant. Offline evaluation already answered whether this works — decisively. What's left is validating it against real traffic before flipping the switch, because the offline eval set is 287 hand-authored, single-register queries and production traffic is not.

Size — S
1 flag flip + 1 route query swap
The code path is already written and gated (SHADOW_LOOKUP_ENABLED). The actual line-count change is tiny — most of this ticket's cost is calendar time (the soak period) and judgment (reading disagreements), not implementation.
Impact — very high
+12.9 to +15.7pp lenient R@1, echo 44%→14%
Directly fixes the single largest, most structural limitation this app has measured — larger than the fine-tune's own contribution (+4.5pp) by roughly threefold. This is the highest-impact ticket in the set.

Task

  1. In app/api/lookup/route.ts, flip SHADOW_LOOKUP_ENABLED to true. Leave SHADOW_SAMPLE_RATE at 0.1 unless traffic volume argues otherwise — re-derive from expected daily query count, not a guess.
  2. Deploy. Confirm [lookup] shadow log failed does not appear in logs (it would mean GlossEmbedding isn't populated — check RD-01 landed first).
  3. Let it run for a real soak period — long enough to accumulate a few hundred sampled queries at minimum, across normal daily/weekly traffic patterns, not a single afternoon.
  4. Run npx tsx scripts/shadow-compare.ts. Read its disagreement sample by hand — this is qualitative review, not just the headline agreement rate.
  5. Decide: cut over, iterate, or hold. If cutting over — swap the route's primary query from VocabEmbedding to GlossEmbedding, keep VocabEmbedding live as an instant rollback path (its data and exact-scan capability still exist per RD-01), and only then consider actually removing the old code path in a follow-up.

Prerequisite knowledge

Why the offline numbers alone don't authorize a cutover

scripts/shadow-compare.ts's own header comment is explicit about this: it can report agreement rate between the old and new systems on live traffic, never accuracy, because no query text has ever been logged and there is no ground-truth label for a real user's query. The eval set's McNemar result (below) is the prior; shadow agreement is the live-traffic sanity check against that prior — not a replacement for it, and not a second independent accuracy measurement.

The offline result this is acting on

Recall and echo move together — the fix targets the actual mechanism, not just the score

Reading list

  • CLAUDE.md §"Headline results" — the full 10-cell table this ticket's chart is one slice of.
  • lib/shadowLookup.ts header comment — what's logged (hash + top-1 only) and why, and the privacy invariant it preserves.
  • scripts/shadow-compare.ts header comment — why McNemar doesn't apply here even though the machinery is imported.
  • The lexical-echo phenomenon itself: CLAUDE.md §"Established facts" — echo results outscore the true target by +0.134 mean cosine on the old index. This is why a reranker over top-10 wouldn't have fixed this; the target sits below nearly everything returned, so there's nothing to reorder.

Learnings

✓

The fine-tune was never the lever. Fine-tuned vs. base model on the same lemma index: only +4.5pp, below the pre-committed 6pp bar for calling it real — a null result despite p=0.029. Swapping what's indexed beat retraining the model by roughly threefold. Don't let "should we fine-tune more" compete for priority against this.

✓

The approximate index and junk-vocabulary filtering are both confirmed non-issues. IVFFlat vs. exact scan costs ~0.3pp (p=1.0); --filter-junk moves recall 0.0pp. Neither is worth re-investigating as part of this rollout if the shadow numbers look off — look at the representation, not the index mechanics.

✓

Sense-familiarity tie-breaking is real but should be cited carefully. WordNet's own within-synset lemma order beats alphabetical by 2.5pp on identical vectors. It's a genuine effect (a person really is more likely to mean the common sense of a word), but it was also selected because it scored best on this eval set — mild benchmark-fitting. Keep both facts attached whenever this is cited.

!

This app's search UX doesn't currently show a ranked list from a single call — check what "top-1" means for the current UI. The route returns a list of k results with similarity scores; the frontend's results page already renders the full list (not just a single top pick), so a gloss-index cutover changing which words appear in that list is user-visible immediately, not hidden behind a "top pick" abstraction. Sanity-check the results page rendering with gloss-index output before considering this done, not just the API contract.
