Build a real-phrasing eval set from public single-word-request threads

P1 · evaluation
Depends on: RD-02's cutover landing first Touches: eval/sets/ (new file, never v1), a new harvest script in scripts/ Risk: a biased set cited as if it were representative Est: 1–2 days of tooling, plus a manual review pass over a few hundred rows

This project has never had a sample of real user queries — first by design (no query text is ever logged), and now by circumstance (there is no traffic to log). RD-02's soak gate assumed traffic that does not exist, which is why it deadlocked. Public single-word-request threads are the closest available substitute, and unlike a shadow log they arrive with the answer attached.

Why this ticket exists

RD-02 gated the gloss-index cutover on shadow-log agreement over "a few hundred sampled queries across normal daily/weekly traffic patterns." At current traffic that threshold is never reached. The gate has been retired (see RD-02's decision record) and the cutover decided on offline evidence instead — but the question the soak was standing in for is still real and still unanswered: does the hand-authored eval set's phrasing resemble how people actually ask? That question is what this ticket answers, using public data rather than traffic this app does not have.

Size — M
Trivial harvest, manual extraction pass
The API call is a few lines and needs no auth. The real cost is human: answers are prose, so every target word has to be pulled out and checked by hand. Comparable in effort to how v1.jsonl was originally built.
Impact — high (measurement)
First real-phrasing signal this project has ever had
Every recall number in this repo currently rests on 312 rows authored by one person in one session. This does not improve retrieval by a single point — it tells you whether the numbers that claim retrieval improved mean anything outside that one register.

Task

  1. Harvest. Pull from the free Stack Exchange API — api.stackexchange.com/questions?tagged=single-word-requests&site=english. No scraping and no auth needed at low volume (300 requests/day unauthenticated, 10k with a free key). Record the fetch date and the exact query string in the set's provenance, the same way every run in this project records its config.
  2. Extract targets. The query is the question title plus body; the target is the word given by the accepted or top-voted answer. Answers are prose — "You might want petrichor" — so this is a semi-automated extraction followed by a manual review pass, not a parse. This step is the ticket.
  3. Mark unreachable rows rather than dropping them. If the answer's word isn't in the index, set meta.reachable: false exactly as v1.jsonl already does for its 25 coverage rows. Silently dropping them would quietly inflate recall by removing the questions the system cannot answer.
  4. Tag the leakage class. Some posters quote a dictionary definition verbatim in the question. Those rows are the same contamination shape as gloss_tripwire — give them a meta.leakage marker and exclude them from the headline slice, keeping them only as a regression tripwire.
  5. Write eval/sets/v2-elu.jsonl. New filename, its own recorded sha256, following the existing { id, query, target, source, meta } row shape. v1.jsonl must be byte-identical afterward — verify it, don't assume it.
  6. Run the paired comparison (lemma vs. gloss) through the existing harness rather than a one-off script. This number is what stands in for the soak — it's the check on whether the +12.9pp measured on v1 survives contact with phrasing nobody in this project wrote.

Prerequisite knowledge

What this is, and what it is not

It is labelled, which makes it strictly more informative than the shadow log could ever have been — lib/shadowLookup.ts's header comment is explicit that shadow data can report agreement rate between two systems but never which one is right, because production traffic carries no ground truth. ELU threads carry the answer.

It is also a hard slice. People post to a Q&A site when they are already stuck, so the set over-samples obscure and hard-to-name words. Absolute recall against it will read lower than production would — cite it for the paired lemma-vs-gloss comparison, never as a headline accuracy figure. This is the same discipline CLAUDE.md already applies to the Phase E pool ("absolute recall on a 20k pool is not comparable to production; only the relative comparison across cells is valid").

Licensing, before any of this gets committed

Stack Exchange content is CC-BY-SA, so attribution is required and must live in the set's provenance, not just in a commit message. Separately, SE's terms carry restrictions around AI training use. Evaluation is a different use than training — but confirm that rather than assuming it, and keep this data out of any RD-09 training corpus unless it is separately cleared. The distinction matters precisely because RD-09 is the ticket most tempted to reach for it.

v1's blindness rule doesn't transfer, and doesn't need to

v1.jsonl's entire value rests on being authored blind to every gloss, because the model was fine-tuned on 181,149 WordNet glosses and any gloss-derived query would be ~100% leaked. That specific precaution is unnecessary here for a stronger reason: ELU queries were written by people who had never seen this model or this vocabulary, years before it existed. The leakage risk isn't the authoring process — it's the minority of posts that quote a dictionary, which step 4 handles explicitly.

Why not the alternatives

  • Reddit r/whatstheword — the same shape of data and arguably a broader register, but bulk API access is now restricted/paid and Pushshift is no longer publicly available. Revisit only if the SE harvest comes up short on volume.
  • OneLook — does not publish query logs. Scraping it yields dictionary data, which is closer to what v1 already is than to real phrasing, so it would not answer the question this ticket exists to answer.
  • Synthetic queries from a generative model — would reintroduce a dependency this project deliberately removed on 2026-08-18, and would measure a model's idea of how people talk rather than how people talk.

Learnings

!

The gate RD-02 was waiting on could not be reached. A soak measured in "a few hundred sampled queries across normal traffic patterns" never completes on an app with no organic traffic, and no amount of patience changes that. "Wait for traffic" was a deadlock wearing the costume of a plan. Worth remembering the next time a gate is written in units of traffic — check that the traffic exists before making a decision depend on it.

✓

A labelled public set beats an unlabelled private one. The shadow log was the more "authentic" data source and still the weaker instrument, because it had no ground truth — it could only ever say the two systems disagreed, not which was right. Authenticity of source is not the same as usefulness of signal.

!

Single-register was v1's stated limitation and this only partly fixes it. ELU is one community with its own house style — more formal, more lexically sophisticated, and more likely to have already tried a thesaurus than a general audience. This trades "one author in one session" for "one community," which is better but is still not a sample of your users. State that wherever the set is cited, the same way v1's limitation is stated.

Acceptance criteria

  • Harvest script committed; fetch date and exact API query recorded in the set's provenance
  • Targets extracted and manually reviewed; unreachable rows marked reachable: false, not dropped
  • Dictionary-quoting rows tagged as a leakage class and excluded from the headline slice
  • CC-BY-SA attribution recorded in the set's provenance
  • eval/sets/v2-elu.jsonl written with a recorded sha256; v1.jsonl verified byte-identical afterward
  • Paired lemma-vs-gloss comparison run and recorded following CLAUDE.md's "Headline results" convention
  • The set's biases restated wherever it is cited: hard slice, single community, not a sample of real users
