Glossary

Every word the tickets use without stopping to explain it. This is a reference — look things up as you hit them, rather than reading it straight through. Terms are grouped so that related ones explain each other, and most carry a real example from this app.

If you read only one entry

Read echo, in "How we measure it". The app's central problem was that a search for "the smell of rain on dry earth" returned raininess, rainstorm, raindrop — words that echo your own words back — instead of petrichor. Almost every ticket here is either a step toward fixing that or a way of checking whether it got fixed.

1 · The words themselves

The app's vocabulary comes from WordNet, an academic dictionary with a specific structure. Three of its terms do most of the work in these tickets.

lemma

One dictionary word, on its own, with no definition attached.

e.g. petrichor — just the word, nothing else
synset

A group of words that all mean the same thing, sharing one definition. Short for "synonym set". A word with several meanings belongs to several synsets.

e.g. { car, auto, automobile, motorcar } is one synset — four words, one meaning
gloss

The definition text belonging to a synset. When these tickets say "the gloss index", they mean a search index built from definitions rather than from the words themselves.

e.g. the gloss of that synset is "a motor vehicle with four wheels"
WordNet

The free Princeton lexical database this app's whole vocabulary comes from. It supplies the lemmas, the synsets, and the glosses. Version 3.0 here.

vocabulary

The full set of words the app can possibly return — 141,854 of them. If a word is not in the vocabulary, no amount of improvement will make search find it.

POS

Part of speech — noun, verb, adjective, adverb. Used to check that a change helps all kinds of word equally rather than only nouns.

2 · How search actually works

There is no keyword matching anywhere in this app. Everything is done by turning text into lists of numbers and finding the closest ones.

embedding
(a "vector")

A list of numbers representing a piece of text's meaning. This app uses 384 numbers per text. Texts that mean similar things get similar lists — which is the whole trick, because it lets a computer compare meaning without understanding language.

"a small dog" and "a tiny hound" land close together; "a small dog" and "tax law" land far apart
cosine similarity

The measure of how close two embeddings are. Runs from 1.0 (identical meaning) down to 0 and below (unrelated). Every "similarity" number in these tickets is this.

semantic search

The whole approach: embed the user's description, then find the stored embeddings closest to it. Because it compares meaning rather than spelling, it can match a description to a word that shares none of its letters.

index

The stored table of embeddings that search looks through, plus the structure that makes looking fast. This project has two: the lemma index (one entry per bare word) and the gloss index (one entry per definition). Switching from the first to the second was the biggest win the project has had.

exact vs.
approximate (ANN)

An exact search compares your query against all 117,791 entries — always right, but slow. An approximate search (ANN, "approximate nearest neighbour") checks only some of them and is occasionally wrong, but is fast enough to use live. Production uses approximate; the tickets measure how much that costs.

measured here: about 0.3 of a percentage point — approximation is nearly free
IVFFlat

The particular approximate method in use. It sorts all the entries into clusters up front, then at search time only looks inside the clusters nearest your query.

probes

How many of those clusters a search bothers to open. More probes means slower but more accurate. Tuning this from 10 to 40 was worth 5.5 percentage points of accuracy for about 20 milliseconds — one of the cheapest wins in the project.

pgvector

The Postgres extension that lets the database store embeddings and sort by similarity directly, so no separate search service is needed.

halfvec

Storing each of the 384 numbers at half the usual precision, halving the space the index takes. Measured here as free — results were identical. Cutting the count of numbers from 384 to 256, by contrast, cost real accuracy.

3 · How we measure whether it works

This is the densest vocabulary in the backlog, and the most worth learning — nearly every claim in every ticket is stated in these units.

eval set

A fixed list of test questions with known right answers — 405 rows in eval/sets/v1.jsonl. Every change is scored against the same list so improvements can be compared honestly rather than by impression.

recall
(R@1, R@10, R@100)

How often the right answer shows up in the top N results. R@1 is "was it the very first result" — what a user actually experiences. R@10 is "was it anywhere on the first page". The gap between them is how much better things could get by re-ordering alone.

today: R@1 is 24% and R@100 is 77% — so 53% of searches find the answer but bury it
strict vs. lenient

Two ways of scoring the same result. Strict counts only the one exact target word as correct. Lenient also accepts pre-approved synonyms.

Lenient is the number this project decides on, deliberately: if someone describes a car and gets automobile, that is a correct answer, not a miss. This matters — it is the reason RD-15 argues against training the model to tell synonyms apart.

acceptable[]

The list of synonyms recorded on a test question that count as correct answers. 133 of the 312 real test questions have one. Where a question has none, lenient scoring falls back to strict.

MRR

Mean Reciprocal Rank — one number summarising how high up the right answer landed, rather than just whether it made the top N. Rewards moving an answer from 5th to 2nd, which plain recall ignores.

echo

A result that just hands you back a word you already typed, in a different form. This was the app's central defect and the reason the whole gloss-index project happened.

searching "the smell of rain on dry earth" returned raininess, rainstorm, raindrop — never petrichor echo rate fell from 40.7% to 14.5% when search moved to definitions. It is tracked on every run: a change that improves accuracy without moving echo is treated as suspicious.
reachable

Whether the right answer even exists in the app's vocabulary. Unreachable questions are kept in the test set but excluded from headline scores — dropping them entirely would flatter the numbers by deleting the questions the app cannot possibly answer.

held-out split

Data deliberately kept away from training so it can be used to test afterwards. Without one, a model can score well purely by having memorised its training data.

The original fine-tune here had no held-out split at all, which is why its reported 10.9% figure is treated as unusable throughout these tickets.

leakage /
tripwire

Leakage is when test questions overlap material the model already trained on, making scores look better than reality. Tripwire rows are knowingly-leaked test rows kept aside purely to catch catastrophic breakage — never quoted as a headline score.

McNemar
(paired comparison)

A statistical test for "is this change real, or just noise?" It compares two systems question by question, counting where one wins and the other loses. With only ~300 test questions, comparing two overall percentages cannot detect a change of a few points — this can.

frozen set /
sha256

The test set is never edited once built; a new version means a new filename. Every run records a sha256 — a fingerprint of the file's exact contents — so that a silent edit is detected instead of quietly invalidating every past number.

4 · The models

The app runs one small language model today. Several tickets are about training it better, or adding a second one.

bi-encoder

What the app uses now. It reads your query and each candidate separately, turning each into an embedding, then compares the numbers. Fast, because every candidate's embedding is computed once in advance and reused forever.

cross-encoder

A slower, usually more accurate model that reads your query and one candidate together, as a pair, and scores how well they match. It can weigh the two texts against each other directly, which a bi-encoder never gets the chance to do.

Too slow to run against 117,791 candidates — but perfectly affordable against 50. That was the idea behind RD-12, and when measured here an off-the-shelf one made results worse, not better. "More accurate" is a property of the data a model was trained on, not of the architecture.

reranking

The two-stage pattern that combination enables: a fast model picks the best 50 candidates, then a slower model re-sorts just those 50 before showing them. You get most of the slow model's quality at close to the fast model's cost.

the ceiling here is real — the right answer is already in the top 100 for 77% of searches — but RD-12 found no off-the-shelf model that could reach it
shortlist

The handful of candidates the fast first stage hands to the slow second stage. Its depth is a budget: too shallow and the right answer was already thrown away before reranking starts, too deep and you pay for scoring candidates nothing could rescue.

a 50-deep shortlist contains the right answer 72.5% of the time; a 10-deep one, only 51.9%
MS MARCO

A large public collection of real Bing search queries paired with web passages, and the standard training set for off-the-shelf rerankers. A model trained on it has learned what makes a web page relevant to a search query.

That is not this problem. A reverse-dictionary query is a description of a meaning, and the candidates are dictionary definitions — and RD-12 measured the mismatch rather than assuming the transfer.

logit

The raw, unbounded number a model emits before it is squashed into anything human-readable. Bigger means "better match"; the absolute value means nothing on its own and cannot be compared across models.

useful for sorting, useless as a percentage — which is why a reranked score cannot simply be dropped into a field that used to hold a 0–100% similarity
fine-tuning

Taking a general-purpose model and training it further on your own data. This app's model is a fine-tune of a public one. Measured here, the fine-tuning bought +4.5 points — less than swapping what gets indexed bought for free.

contrastive
training

How these models learn: show them a correct pair and some incorrect ones, and push the correct pair's embeddings together while pushing the wrong ones apart. Repeat a few hundred thousand times.

hard negatives

Deliberately chosen wrong answers that are nearly right, used during training. Learning to reject a plausible wrong answer teaches more than rejecting an obviously unrelated one — that is the theory RD-15 examines and partly pushes back on.

ONNX

A portable file format for trained models, letting one trained in Python run in a JavaScript server. The app's model is an 86MB ONNX file.

quantization

Shrinking a model by storing its numbers less precisely. Faster and smaller, slightly less accurate. Noted in these tickets mainly because no quantized version of this model exists — a fact that has been mistaken for a tuning choice.

5 · Running it in production

Terms from the deployment side, which several tickets turn on.

cold start

The server code that answers a search shuts down when nobody is using it, and must start up again for the next visitor. That first request is the cold start.

it used to take 43 seconds here, because the 86MB model was re-downloaded each time. Now 64 milliseconds.
function bundle

The package of code and files shipped to the server for one API route. Anything not in the bundle has to be fetched over the network at run time — which is exactly what made cold starts slow until the model was put inside it.

file tracing

The build step that decides which files go into that bundle. It over-includes by default: here it was packing model runtimes for Mac and Windows into a bundle that only ever runs on Linux, wasting 43.7MB.

migration

A recorded, repeatable change to the database's structure — adding a table, dropping a column. Kept as files so the same change can be applied to every copy of the database in the same order.

Neon

The hosted Postgres provider holding the words and their embeddings. Its storage limit is a recurring constraint in these tickets — the embeddings are large, and there was for a while no room for a second index.

region (iad1)

Where the server code physically runs — here, northern Virginia, the same place as the database, so they can talk to each other quickly. Worth knowing because timings measured on a laptop include a long round trip that real users never pay.

shadow logging

Running a proposed new system alongside the live one and recording where they disagree, without showing anyone the new results. Tried here, and abandoned — it can tell you two systems disagree but never which one was right, and the app had too little traffic to gather enough of it.
