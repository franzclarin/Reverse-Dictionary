An interactive 3D explainer for the retrieval pipeline

✓ Done
In plain terms

Nobody can see what this app does. You type a sentence, a word comes back, and everything in between is a black box — including to people who have read the whole backlog.

Today — the pipeline is explained in prose across CLAUDE.md, this backlog and the glossary. All of it is accurate and none of it is visible.

Do — a page at /explain where you type a phrase and watch it happen: the sentence broken into pieces, those pieces becoming one arrow in a cloud of meanings, the nearest meanings lighting up, and a ranked list of words with their real scores.

Why it matters — it teaches the one thing the prose keeps failing to convey: this app never matches words, it matches meanings, and the thing it ranks is not a word at all — it is a synset, which then bursts into several words that all score identically.

Result — done 2026-08-28. Shipped at /explain. Nothing was served into the search path and no metric moved, by design.

Result — done 2026-08-28

The page runs the real pipeline on whatever you type. It calls the same /api/lookup with an opt-in debug flag, so every score comes from the live 117,791-synset index through the served code path; with the flag off the SQL is character-identical to what it was before, and a frozen copy of that SELECT is asserted in scripts/verify-viz-snapshot.ts so a future edit breaks a test rather than a promise.

Two things cost more than planned and were worth it. First, the animation needed data that did not exist: showing each word being embedded is only honest if each token's vector is the real one, and the API returned just the pooled vector. embedTokens() now takes one pooling: "none" pass and derives the pooled vector from it — and the harness asserts that derivation equals embed() to 2.2e-8, so the averaging on screen is the actual arithmetic. Second, the browser tokenizer was reimplemented rather than imported, to keep ~1 MB of Transformers.js out of a page whose whole argument is that the model stays on the server; it is checked against the real AutoTokenizer over 415/415 strings.

Measured and displayed: three principal components carry 11.9% of the variance in 384 dimensions. /explain first-load JS is 102 kB, and its function traces 20 files, none of them the model.

A reverse dictionary is an unusually good thing to visualise, because its entire mechanism is geometric: a sentence becomes a point, and the answer is whatever is nearest. That is genuinely drawable, unlike most of what a model does. The catch is that the space has 384 dimensions and the screen has three, so every frame of this thing is a projection — and the whole ticket turns on being loud about which parts are real measurements and which parts are stagecraft.

Task

  1. Trace the pipeline before drawing it. Done — see Prerequisite knowledge below. The trace is in this ticket because a generic "tokenize → embed → rank" diagram would be wrong about this system in two specific ways: there is no reranking stage, and the thing being ranked is a synset rather than a word.
  2. Precompute the snapshot offline (scripts/build-viz-snapshot.ts). Sample a few thousand synsets from GlossEmbedding, fit PCA over their vectors, and emit one static JSON: the 384×3 basis, the mean vector, per-synset 3D coordinates, lemmas, gloss text, and the measured variance explained by the three components. Import embed from lib/embedder.ts if any embedding is needed at all — never a second encoder, the same rule the eval harness enforces.
  3. Add a dev-gated debug field to /api/lookup returning the query's 384-d vector and the retrieved synsets with their gloss text. searchGlossSynsets(prisma, vec, k, probes, { withGloss: true }) already returns that shape. Gate it — with withGloss off the query is byte-identical to today's, and that property is deliberate and worth keeping in production.
  4. Tokenize in the browser, for real. Load only the tokenizer from models/franzclarin/ReverseDictionary/tokenizer.json (~700 KB) — not the 86 MB model. The sub-words shown on screen are then the actual sub-words the server fed to the encoder, not a plausible-looking split.
  5. Build the stage sequence — tokens → pooled vector → arrival in the cloud → neighbours lighting up → camera flight → synset expansion → ranked list. Each stage gets a caption that names the operation, not just narrates it: "mean pooling", "cosine similarity, computed in 384 dimensions", "IVFFlat, 40 probes of 115 lists".
  6. Project returned synsets through the shipped basis. A result that is not in the sampled cloud must still appear in exactly the right place, which works because PCA is a fixed matrix and the debug field returns the vectors. Do not fake a position by averaging neighbours.
  7. Label every approximation on screen, from the list below. This is the acceptance-critical step, not the polish step.
  8. Decide whether it is public. A dev-gated debug field and a public page are in tension. Either gate the route with the field, or have the page degrade to a precomputed demo in production.

Prerequisite knowledge

The pipeline as it actually is

Traced through app/api/lookup/route.ts → lib/embedder.ts → lib/glossSearch.ts, plus models/franzclarin/ReverseDictionary/config.json. Read this before drawing anything.

#stagewhat actually happenswhere
1requestPOST {query, k=10}, 500-character capapp/api/lookup/route.ts
2tokenizeBERT WordPiece, lower-cased, wrapped in [CLS]…[SEP], vocabulary of 30,522 pieces, truncated at 256tokenizer.json
3encodeBertModel, 6 layers, hidden size 384, 12 attention heads — the all-MiniLM-L6-v2 architecture, fine-tuned. No decoder, which is why word pages have no definitionsconfig.json
4pool{ pooling: "mean" } — the per-token outputs averaged into one vector, [CLS] and [SEP] included. Reproduces the sentence-transformers Pooling layer that seeded the databaselib/embedder.ts
5normalize{ normalize: true } → unit-length 384-d vector, so cosine similarity is a plain dot productsame
6retrieveSET LOCAL ivfflat.probes = 40 inside a transaction, then ORDER BY embedding <=> $1::halfvec LIMIT k over GlossEmbedding — 117,791 synsets, halfvec(384), IVFFlat with lists = 115lib/glossSearch.ts
7expandThe step a generic diagram would miss. Rows are synsets, not words. expandSynsets() unpacks each into its member lemmas in WordNet's own order, dedupes across synsets, truncates to k. Every word inherits its synset's score — so synonyms come back at identical similaritylib/glossSearch.ts
8render{ results: [{word, similarity}], timingMs } → navigate to the top word, runners-up as ?alternatives=route + app/page.tsx

There is no reranking stage and no generative model anywhere in this. RD-12 measured a cross-encoder and rejected it; the generative dependency was removed on 2026-08-18. A diagram showing either is a diagram of a system this repo does not have — and both are exactly what someone would draw from memory of how retrieval systems usually look.

The reduction is PCA, and the reason is not aesthetics

PCA is the only one of the three candidates that is parametric: it fits once, offline, and produces a fixed 384×3 matrix. A new query projects through that same matrix instantly, deterministically, and in the same frame it arrives.

methodnew point without refitting?verdict
PCAyes — one matrix multiplyUse this. Layout is stable across queries, and any synset the API returns can be placed exactly rather than guessed.
UMAPno — needs a refit or an approximate transformPrettier clusters, but the world would shift between queries and a live typed phrase has no honest position in it.
t-SNEno, and it has no out-of-sample transform at allAlso actively distorts global distance, which is the one quantity this page exists to show.

The cost is that three principal components carry only a modest share of 384-d variance. Measure it in step 2 and print the number on screen. An unlabelled projection invites the viewer to read distances off the picture, which is exactly the wrong lesson.

The four things that must be labelled as approximated

  1. 3D distance is not the ranking. Scores are cosine similarity in all 384 dimensions; the picture shows three. A true nearest neighbour can appear far away, and two points that look adjacent may be unrelated. This is the single most misleading property of the page and needs permanent on-screen text, not a footnote.
  2. The cloud is a sample. A few thousand synsets, not all 117,791. Retrieval always searches the full index.
  3. The vector is computed on the server. Tokenization in the browser is real; the encoding is not local. The model is 86 MB of ONNX and there is no quantized artifact — CLAUDE.md records that model_quantized.onnx does not exist on the hub, and that producing one would change query vectors and require a full eval:prod behind it. Shipping it to a browser is not a tuning decision, it is a new experiment.
  4. The IVFFlat partition cannot be drawn. probes = 40 over lists = 115 is a partition of a 384-dimensional space. Any 3D cell boundary is a metaphor. Either say so explicitly or demote it to the 2D schematic.

Two things worth showing precisely because they are counter-intuitive

  • Ties are real and they are policy. Synset mates carry bit-identical vectors, so retrieval genuinely cannot separate them; their order comes from WordNet's own within-synset ordering, which is a familiarity prior. CLAUDE.md measures that choice at 2.5 points of lenient R@1 over alphabetical ordering, on identical vectors. A visualisation that shows the tie makes that legible in a way the prose has not.
  • Echo is visible in the geometry. Type a query containing rain and the echo results are not merely wrong, they sit closer than the right answer. That is the entire backlog in one frame, and it is the strongest argument for building this at all.

Reading list

  • lib/glossSearch.ts — the file header is the authoritative statement of expansion semantics, and warns that changing them invalidates the measurement RD-02 shipped on.
  • lib/embedder.ts — pooling and normalisation, and the warning that Transformers.js's env is a process-wide singleton that must be configured at the call site. A browser-side tokenizer load is a fourth consumer of that singleton and the same rule applies.
  • RD-12 — why there is no rerank stage to draw, and where searchGlossSynsets() came from.

Learnings

!

The obvious diagram of this system is wrong in two places. Drawn from memory, a retrieval pipeline has a reranking stage and ranks documents that are words. This one has no reranker — RD-12 measured and rejected it — and it ranks synsets, which then expand into several words at identical scores. Both errors would look entirely plausible on screen. Trace before you draw, and put the trace in the ticket so the next person does not re-derive it from a stock picture.

✓

The reranker seam is the visualisation seam. searchGlossSynsets() was split out for a cross-encoder that never shipped, and it returns exactly what this page needs: the synsets, their gloss text and their scores, before anything collapses them into words. A refactor done for a rejected experiment left the codebase better shaped for an unrelated one.

!

The animation needed data the API did not have, and that was the whole test of the ticket. "Show each word being embedded" has a cheap version — draw something plausible under each token — and it would have looked identical to the honest one. The honest one required embedTokens(): one pooling: "none" forward pass returning the encoder's real per-token output, with the pooled vector derived from it rather than fetched separately. What made it safe to claim was not care, it was the assertion — the harness checks that derivation against embed() and gets 2.2e-8. When a picture asserts an arithmetic relationship, test the relationship.

✓

Reimplementing the tokenizer was cheaper than importing it, and better documented. Loading AutoTokenizer in the browser would have pulled ~1 MB of Transformers.js and the onnxruntime-web loader into a page whose central claim is that the 86 MB model never reaches a browser. ~100 lines of WordPiece instead, checked against the real tokenizer over the entire frozen eval set plus deliberately awkward strings — 415/415 identical. The check paid for itself immediately by catching a real quirk: an over-long input loses its [SEP], because truncation runs after post-processing appends it. The tidier algorithm would have been wrong.

!

Building the explainer surfaced a live bug in the thing being explained. Neon auto-suspends its compute, and Prisma's default 2s interactive-transaction maxWait is shorter than the wake-up, so the first query after an idle period died with P2028 — a 500 with nothing wrong with the query. The eval harness had always worked around this by warming the database first, which is why it never showed up as a serving problem. A page that invites strangers to type a phrase has no warm-up. searchGlossSynsets() now waits instead.

✓

Three layouts were built and two were thrown away, on purpose. The shared engine — projection, canvas, panels, run hook — was built once, so each shell was ~150 lines of chrome over it. Choosing between three real pages taking a real query beat choosing between three descriptions, and the two rejected ones cost almost nothing because the expensive part was never duplicated.

✓

The forecast dependency was not needed. This ticket named three in its own Touches line. 6,200 points with an orbit camera and a painter's-algorithm depth sort is a canvas-2D job, and drawing depth as radius-and-alpha is two lines by hand against a custom shader in WebGL. The repo still has five production dependencies.

!

A projection is a claim about distance, and viewers will believe it. The reason to choose PCA here is not that it looks best — it does not — but that it is a fixed matrix, so the layout does not move between queries and every returned point can be placed exactly rather than interpolated from its neighbours. Choosing UMAP for prettier clusters would mean the query's own position is invented, which is the one point on screen that must not be.

Acceptance criteria

  • Every similarity score displayed comes from the real retrieval path over the live 117,791-synset index — no fabricated or interpolated scores anywhere — the page calls /api/lookup with debug: true; the harness asserts the debug branch returns the same words as the serving branch.
  • Tokens shown are the tokenizer's actual output, not a whitespace split dressed up as sub-words — lib/viz/wordpiece.ts, checked against the real AutoTokenizer on 415/415 strings including accents, OOV, CJK and truncation.
  • The synset → lemma expansion is visibly distinct from ranking, and tied scores are shown as tied — stage 7 bursts one sense into its member words at identical scores, and the ranked list marks tied rows as tied.
  • PCA variance explained is measured in the build script and displayed on the page — 11.9%, measured in scripts/build-viz-snapshot.ts and printed beside the cloud.
  • All four approximations from the list above are labelled in the interface, not only in this ticket — permanently, along the bottom bar; they deliberately do not hide with the steps card.
  • Any synset returned by a query is placed at its exact projected position, including ones absent from the sampled cloud — asserted to 4.6e-5 against the snapshot coordinates; the API returns the stored vector and the client projects it through the same fixed basis.
  • Orbit and zoom controls work, and the camera can be taken back to a known home view — drag, scroll, and a ⌂ home button; the camera also flies to frame each result.
  • No change to /api/lookup's existing response shape, and the production query stays byte-identical with the debug field off — results and timingMs untouched; the SELECT is asserted character-identical to a frozen copy. k is now validated, which it was not before.
  • The 86 MB model is never downloaded by a browser — verified in the network panel: only the two /viz/ assets and /api/lookup. The route traces 20 files, none of them the model.
  • Stage captions name the operation — "mean pooling", "cosine similarity" — rather than only narrating it — the operation name rides on the animation itself, so it is on screen even with the prose hidden.
