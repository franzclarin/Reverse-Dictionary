Show the definition the database already has

P1 · product
In plain terms

Every word page says what the word is near. None of them says what it means — even though the meaning is sitting in the same database, one column away.

Today — /word/selfie renders a heading, a list of related words, and no definition. Meanwhile GlossEmbedding holds "A photographic self-portrait, especially one taken manually with a smartphone" for that exact word, because that sentence is what search matched the query against in the first place.

Do — read the gloss the retrieval already used and put it on the page.

Why it matters — this is not new content to acquire, generate or pay for. It is content the app fetches, ranks on, and then throws away before rendering. RD-17 multiplied it by six without anyone noticing it was there.

Depends on: nothing — RD-17 made it much more valuable but it was already true Touches: lib/wordData.ts, app/word/[word]/page.tsx, prisma/schema.prisma (maybe) Risk: low on retrieval (it changes nothing in the search path) — the real questions are sense selection and licensing Est: S — a day, most of it deciding which sense to show

Measured on the live database, 2026-08-28: 332 of the 477 rows in Word have an empty definition, and all 519,793 answerable lemmas have a gloss in GlossEmbedding. The app has never had more text about words than it does right now, and it displays none of it.

A reverse dictionary that hands you a word and cannot tell you what it means has finished half the job. This is the cheapest remaining improvement to what a user actually sees.

Task

  1. Read the gloss, do not store a copy. GlossEmbedding.gloss is the text retrieval scored against, so displaying it means the page shows the reason the word was returned. Copying it into Word.definition would create a second source that can drift from the index — and Word already has 332 empty rows demonstrating how that goes.
  2. Decide which sense leads, and make the rule visible. A polysemous word has several rows. Two defensible options: WordNet's own sense order (a familiarity prior, the same policy expandSynsets() already uses for tie-breaks), or the sense whose vector is nearest the query that brought the user here. The second is better and needs the query, which the page only has via ?alternatives= — decide deliberately rather than taking whichever ORDER BY id returns.
  3. Show more than one sense where they exist. capsize has one gloss; cat has many. Showing a single arbitrary one is worse than showing three labelled ones.
  4. Attribute per source, because they differ. WordNet 3.0 senses (<pos>:<offset> keys) need attribution. Wiktionary senses (wikt: keys) are CC BY-SA — attribution and share-alike. The key already says which, so the page can label each gloss correctly rather than carrying one vague footer. /explain already does this; word pages do not.
  5. Revisit the empty-row design while you are here. getWordData() upserts a minimal Word row on every visit to an answerable word. That was a bounded oddity at 141k answerable words; it is a different proposition at 519,793. If the definition now comes from GlossEmbedding, ask whether the Word row needs to exist at all for a word with nothing else on it.
  6. Do not touch the search path. This is a rendering change. Nothing here should alter what /api/lookup returns, and no eval number should move. If one does, something was wired wrong.

Prerequisite knowledge

Why the page is empty, which is not an oversight

Claude was removed from this project in 2026-08, and word pages were rebuilt around the embedding model alone. CLAUDE.md is emphatic and correct that an embedding model has no decoder and cannot produce a definition. That reasoning is about generating text. It has been quietly read as "the app cannot show definitions", which is a different claim and is no longer true: RD-02 put a human-written definition behind every sense in the index, and RD-17 added half a million more. Reading stored text is not generation.

The gotcha that is already written down and now matters more

getWordData() creates rows with definition: "" that are indistinguishable from a real profile by presence alone. CLAUDE.md already warns that any future generative source must regenerate on definition === "", not on row-absence. That warning applies to this ticket too, in reverse: if a page falls back to Word.definition when present, then petrichor keeps showing the model-written sentence forever and never shows the sourced one. Decide which source wins, explicitly.

What this is not

Not etymology, pronunciation, or example sentences — none of those are in the database and none can be derived from a vector. The scope is exactly the text that already exists.

Reading list

Learnings

!

A correct constraint outlived the situation that made it true. "The model cannot write a definition" is right, was load-bearing when the generative dependency was removed, and got compressed into "the app has no definitions" — which stopped being true the moment search started matching against sense definitions. The index has held this text since RD-02. Nobody looked, because the constraint sounded settled.

✓

Showing the gloss shows the reason. The text this ticket renders is not merely a definition — it is the exact string the query was scored against. A user who sees it can tell whether the match was sensible, which is the same argument RD-18 makes for /explain, available on every result page for the cost of one column.

Acceptance criteria

  • Word pages render the stored gloss for any answerable word, read from GlossEmbedding rather than copied into Word
  • Sense-selection rule chosen deliberately, stated in code comments, and visible to the reader when a word has several senses
  • Per-source attribution on the page — WordNet and Wiktionary labelled separately, with CC BY-SA share-alike named for the latter
  • Precedence between Word.definition and the stored gloss decided explicitly, with the 145 Claude-era rows considered by name
  • The empty-Word-row design revisited against 519,793 answerable words, and either justified or changed
  • No change to /api/lookup and no movement in any eval number — verified by a run, not by inspection
