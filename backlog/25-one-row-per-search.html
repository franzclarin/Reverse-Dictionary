One row per search, not two

✓ Done P1 · instrumentation
In plain terms

Today — RD-24 started writing down every search. Every search typed into the site produced two identical entries.

Done — one entry per search. The site was sending each search twice; it now sends it once, and the database refuses a second copy even if something sends one anyway.

Why it matters — a log that double-counts is worse than no log, because it looks like data. But the more interesting part is that the second request was always being sent — for months, costing a full search each time. Writing things down is what made it visible.

Status: done 2026-09-01 — verified in development and in a production build Touches: components/SearchResults.tsx, app/search/page.tsx, lib/queryLog.ts, app/api/lookup/route.ts, one migration Does not touch: retrieval — the frozen set, every committed run and the serving query are unchanged Found by: looking at the table RD-24 had just created

The duplicate was not in the code RD-24 added. It was in code that had been sending two requests per search since long before, and had simply never left a trace.

The two causes

1 · A side-effecting effect with no cleanup

next.config.js sets reactStrictMode: true. In development React mounts, unmounts and remounts every component, running each effect twice — deliberately, to expose effects that are unsafe to repeat. The effect in components/SearchResults.tsx POSTs to /api/lookup and had no cleanup function at all, so both invocations reached the server.

The existing requestIdRef guard looks like it handles exactly this, and does not: it suppresses stale state updates, while the discarded request still travels the network and still costs a full embedding plus pgvector lookup. That waste is months old. RD-24 did not introduce it — it made it observable.

The evidence was in the rows rather than in the reasoning: both carried identical k and resultCount, and createdAt − timingMs put the two start times 1 ms apart. Two rows that start together are one client firing twice, not one server writing twice.

2 · Two effects racing over k — and this one was not development-only

A second effect synced the result count back to 10 whenever the query changed, beside the effect that fetches on [query, k]. After a “Load more” (k = 20), typing a new query fired the fetch with the stale k = 20, then again with the reset k = 10. Two requests with different counts, in every environment including production. It was absent from the reported symptom only because it needs a Load-more first.

The fix, in two layers

layerwhat it does
Stop sending twiceAn AbortController aborted from the effect's cleanup — the cleanup it never had. Also required: ignoring AbortError in the catch, or a request we cancelled ourselves renders as a user-facing error message and an error sound.
Reset with a key, not an effectapp/search/page.tsx passes key={query}, so a new query is a new component instance with fresh state. The syncing effect is deleted. React's own documented pattern, and it removes code rather than adding it.
Refuse a second copyA searchId per search, with a @unique index and ON CONFLICT DO NOTHING. A duplicate arrival is skipped rather than written, whatever the client does.
The detail that decides whether any of it works

The id must identify the search, not the request. Generating it inside the effect produces a different id on each of StrictMode's two runs and buys nothing at all; it is computed with useMemo keyed on the query and the count, so both runs read the same one. Nor can it be a hash of the query text — that would silently discard a legitimate repeat of the same search later. Asking for more results is a different search and correctly gets its own id, which is why “Load more” still logs.

Prerequisite knowledge

Why the production build had to be checked separately

StrictMode's double-invocation is a development-only behaviour, so a fix could pass in next start for the wrong reason — by the bug not being there. Both were run: development first, because that is where the bug reproduces, and a production build afterwards to confirm the result was not an artifact. Cause 2 is environment-independent and was verified in both.

Deliberately not done

The route does not check request.signal. It would save the wasted lookup when an abort loses the race, but the client now rarely sends that request and the unique index makes it harmless if it arrives. Worth its own ticket if the waste ever shows up in practice.

Learnings

!

Adding a log is itself a measurement, and the first thing this one measured was a bug in the client. Every search had been costing two full lookups for months. Nothing surfaced it, because nothing wrote anything down — the duplicate request was invisible precisely because the app was careful never to record queries. Instrumentation pays for itself before it answers the question it was built for.

!

A guard that looks like it handles the case, and does not. requestIdRef reads as request de-duplication and is really display de-duplication: it stops a stale answer being shown, never a stale request being sent. Worth naming, because the code appeared to have already solved this and that is what makes such a thing survive review.

✓

The timestamps identified the culprit before any code was read. Two rows, identical k, and start times 1 ms apart once timingMs was subtracted from createdAt. That is a client firing twice and cannot be a server writing twice — a sequential retry would look nothing like it. Recording how long the work took alongside when it finished is what made the arithmetic possible.

✓

Two layers, because they fail differently. The client fix removes the wasted work but is a race — an abort can lose. The unique index guarantees the row count but leaves the waste. Neither alone is the fix; the split is what makes the log trustworthy and the app cheaper.

Acceptance criteria

  • One search → exactly one row (was two)
  • “Load more” → exactly one more row, at the larger k
  • A new query straight after a Load-more → exactly one row, at k = 10
  • No error flash, no stuck spinner, no error sound from a cancelled request
  • Two requests sharing a searchId → one row; two without one → two rows
  • An over-long searchId is rejected with 400 — it is client-supplied
  • /explain still writes nothing
  • All of the above re-verified against a production build, where StrictMode does not double-invoke
  • Retrieval untouched: npm run verify-viz passes, serving SELECT still byte-identical
