Build the production gloss index under Neon's 512MB ceiling

P0 · data engineering ✓ Done · 2026-08-26
In plain terms

Before search could match your description against definitions, the definitions had to be stored as searchable data. This built that table.

Was — search compared your description against bare words — just petrichor, with no definition attached. The better approach was designed and written but had nowhere to live: the database was nearly full.

Did — built a second index holding one entry per meaning — 117,791 of them, each carrying its definition text.

Result — done 2026-08-26. The plan changed mid-flight: the database plan was upgraded, so the old word-based index did not have to be deleted to make room. Both now exist, which is what made rolling back safe.

Blocks: RD-02 Touches: Neon Postgres, GlossEmbedding, VocabEmbedding Risk: production schema change, index drop Est: ~1–2 hrs execution + ~35 min embed time

The single highest-leverage retrieval fix measured for this app — embedding WordNet definitions per sense instead of bare words — is fully designed, type-checked, and committed as dormant scaffolding. It has never been run against production because doing so requires freeing storage headroom that doesn't currently exist. This ticket is the mechanical work of making room and populating the table. It does not include flipping search over to it — that's RD-02.

Result — plan changed mid-flight

Executed 2026-08-26 after the user upgraded their Neon plan, which removed the original reason for step 3 (the DROP INDEX on VocabEmbedding). That step was skipped entirely — VocabEmbedding and its IVFFlat index are untouched, confirmed live via EXPLAIN (index scan, not sequential scan) after the run. GlossEmbedding now holds 117,791 rows (vs. the ~114,662 estimated here — +2.7%, likely wordnet-db version drift, flagged automatically by the script and not investigated further). Self-retrieval: 60/60 gloss probes by synset, 59/60 vocab probes (pre-existing index-approximation noise, not a regression). Final pg_database_size: 673MB — higher than this ticket's ~452MB estimate because the index-drop was skipped, exactly as expected once that step changed. Not verified against the upgraded plan's actual cap (no Neon CLI access this session) — confirm separately. Full blow-by-blow in MIGRATION_AUDIT.md, "Phase 5."

Prerequisite knowledge

Why this can't just be added alongside the existing index

A prior attempt to stage a second vector index without dropping the first failed outright with Postgres error 53100 project size limit exceeded. This isn't a performance tuning question — it's a hard capacity wall.

Reading list before touching this

  • scripts/build-gloss-index.ts — the script itself; read the header comment before running.
  • prisma/migrations/20260822000000_add_gloss_embeddings/migration.sql — note the *** HARD STOP *** banner around the DROP INDEX line.
  • CLAUDE.md §"Storage ceiling" and §"Phase E" for how the 114,662/88MB/43.9% figures were derived.
  • halfvec vs vector: pgvector 0.8.0's half-precision type. Confirmed lossless at 384 dims (0 discordant pairs against full-precision in the eval cells) — halfvec(256) is a different thing (truncation, not quantization) and costs real recall. Use 384. Don't "optimize" this further without re-reading why.

Learnings

✓

The synset collapse is lossless, not a lossy shortcut. Verified per-query identical to the uncollapsed per-sense version across all 287 eval queries — 0 discordant rank-1 pairs. This was a real open question (flagged "⚠ cross-surface" earlier) and has since been falsified as a concern.

✓

halfvec(384) costs nothing measurable. Mean cos(before, after) = 0.99999998 across the eval cells. This is the fact that makes the storage math close at all — without it, a full-precision gloss index doesn't fit under any index-dropping strategy.

!

The production build differs from the Phase E eval cells on purpose. Eval cells used a matched 20k-word pool restricted to words with WordNet coverage; production indexes the full WordNet lemma set, which incidentally repairs ~5% of VocabEmbedding's coverage gap. Don't expect the eval numbers to transfer 1:1 in absolute terms — only the relative comparison (lemma vs. gloss indexing) is validated. Log actual row counts and revisit if they diverge meaningfully from 114,662.

!

The DROP INDEX step is not reversible without re-running an IVFFlat build. VocabEmbedding's rows survive as an exact-scan rollback, but rebuilding the approximate index afterward (if RD-02 is abandoned) means re-running CREATE INDEX ... USING ivfflat, which itself takes meaningful time on 141,854 rows. Confirm the decision on RD-02's direction before crossing this step, not after. (Moot for the 2026-08-26 run — this step was skipped per the plan change above — but still true if a future run needs it.)

!

The population script's insert phase was ~100x slower than estimated on first run — a real bug, not just pessimistic sizing. The original loop ran 500 sequential single-row $executeRawUnsafe calls per batch inside one $transaction, paying a full Neon round-trip per row; measured at ~90s/500-row batch, projecting to ~6 hours for 117,791 rows against a ~35min estimate. Fixed by collapsing each batch into one multi-row INSERT ... VALUES (...), (...) statement — one round-trip per batch instead of 500. Also hit one transient Can't reach database server failure on the very first run, with zero rows written (safe — no cleanup needed); most likely Neon's compute idling during the ~8.4min DB-silent embedding phase. Both fixes are in scripts/build-gloss-index.ts as of this run; that edit was uncommitted as of the ticket closing — review before relying on the ~35min estimate again.
