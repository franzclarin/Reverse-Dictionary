Wire the reranker into /api/lookup

P3 · infrastructure · blocked
In plain terms

RD-12 built the re-sorting model. This was to be what put it in front of users. It did not happen, and that is the system working.

Today — blocked, and correctly so. RD-12 reported on 2026-08-28: every off-the-shelf reranker it measured made results worse. There is nothing here worth shipping.

Would do — wire a reranker into the live search: the fast search picks 50 candidates, a slower model re-sorts just those, and the page shows the result.

Why it matters — this ticket was deliberately kept separate so RD-12 could come back with a disappointing number and cost nothing. It did, and it did. No deploy, no rollback, no user affected — the gate is the whole value here.

Depends on: RD-12 producing a measured win offline — it did not (2026-08-28, null result) Touches: app/api/lookup/route.ts, lib/glossSearch.ts, a new lib/reranker.ts, scripts/fetch-model.mjs, next.config.js Risk: reintroducing the cold-start regression RD-11 just eliminated; per-request latency from 50–100 forward passes Est: S–M, gated entirely on RD-12's result

The serving half of the reranker, split out deliberately. This is the same build-then-cut-over shape as RD-01/RD-02: measure offline against a frozen set, then take serving risk, so a null result costs no production exposure. Retrieval stays ANN and fast; the cross-encoder only ever sees the shortlist.

RD-12 reported — this stays shut

The gate written here read: "a cross-encoder recovers some fraction of a ceiling, not the ceiling. If that fraction is small, the right outcome is to ship nothing and pay no latency — which is only knowable offline."

The fraction was negative. Three arms of ms-marco-MiniLM cross-encoders scored −3.8, −2.4 and −2.1 points of lenient Recall@1 against plain retrieval; even parameter-free rank fusion reached only +1.8, well under the pre-committed ~6-point bar and itself the maximum of 24 cells picked after the fact. See RD-12 and eval/METHODS.md §13.

The task list below is preserved as-written, unstruck. None of it was executed. It stays because the serving problem it describes — bundling a second model without undoing RD-11, the similarity contract, the third error tag — is exactly the problem any future reranker faces, including a fine-tuned one. Re-open this only when something has cleared RD-12's bar offline.

Task

  1. Keep the API contract byte-identical. /api/lookup returns { results: [{ word, similarity }] }, and that shape survived the RD-02 cutover with no frontend change at all. Decide explicitly what similarity means post-rerank — cross-encoder score or retained cosine — and say so in the route. app/page.tsx and the ?alternatives= query string both consume this, and a score on a different scale is a silent semantic change, not a breaking one.
  2. Retrieve deep, return shallow. route.ts:81 currently calls searchGloss(prisma, vectorLiteral, k) with the caller's k (default 10). It becomes: retrieve the RD-12 shortlist depth, rerank, truncate to k. Note that expandSynsets() already truncates to k after dedup — the reranker has to run on synsets before that truncation, or it reorders a list that has already thrown away its tail.
  3. Bundle the cross-encoder the way RD-11 bundled the embedder. Add its files to scripts/fetch-model.mjs and its directory to outputFileTracingIncludes in next.config.js. RD-11 measured this exact path as 43,050ms → 64ms, and found the wait was 99.8% network. A second model fetched at request time reintroduces that regression wholesale — and lib/embedder.ts runs with allowRemoteModels = false, so the failure mode is a hard error, not a slow request.
  4. Re-check the bundle budget. The /api/lookup function traced at 195.3MB before outputFileTracingExcludes dropped 43.7MB of darwin/win32 ONNX binaries, landing at 151.6MB. CLAUDE.md cites a 250MB legacy ceiling; Vercel's Fluid Compute now allows 5GB. Confirm which limit this project is actually deployed under before treating headroom as either blocking or unlimited — a cross-encoder is small next to the 86MB embedder, but the margin under 250MB is not large.
  5. Measure real latency in iad1, not locally. 50–100 cross-encoder forward passes is real compute against maxDuration = 60. CLAUDE.md is explicit that the harness's db p50 ≈ 466ms is a local-machine-to-Neon round trip and invalid for describing user experience — so the offline numbers from RD-12 say nothing about what this costs a user. Batch the pairs in one forward pass where the runtime allows it.
  6. Give the reranker its own subsystem tag. The route wraps each outbound dependency and throws SubsystemError(subsystem, …) so the log line names the culprit. Today that is model and database. Without a third tag, a reranker fault reads as an embedder fault and sends the next debugging session to the wrong place — exactly the problem the tagging convention exists to prevent.
  7. Reuse the singleton discipline. globalThis._embedderPromise memoises the embedder and clears the slot on rejection, because a cached rejected promise fails every later request on the same warm instance forever. The reranker needs the same treatment, not a fresh implementation of it.
  8. Verify the production path with eval:prod after deploy, the way RD-02 confirmed its offline prediction against the live index. Add the run to eval/runs/ as a committed reference if it becomes the production path.

Prerequisite knowledge

Rollback is one call, and should stay that way

RD-02's rollback story was "reverting the one searchGloss() call in the route is the entire rollback, no data migration." Preserve that property: the rerank stage should be skippable without touching retrieval, so backing it out is one edit rather than an unwind. The gloss index and GLOSS_PROBES are unaffected either way — this ticket adds a stage, it does not change what is stored.

Two models in one function is a new shape for this codebase

Everything CLAUDE.md records about env being a process-wide singleton applies twice over here. env.allowLocalModels / allowRemoteModels / localModelPath must be set immediately before each pipeline() call, never at module scope — two modules setting it at module scope is precisely the bug that broke eval:prod with "both local and remote models are disabled", and adding a third consumer makes that failure more likely, not less.

Learnings

✓

Splitting build from cut-over is what let RD-02 be decided on evidence. RD-01 produced the index, RD-02 decided whether to use it, and when RD-02's soak gate turned out to be unreachable the offline numbers were already sitting there to decide on instead. Same structure here: RD-12 can return a null result and cost nothing but its own time.

!

The cold-start win is fragile and was expensive to find. RD-11 took 43 seconds off the first request, and the diagnosis — 99.8% network, 0.2% compute — is what ruled out both a smaller model and a keep-warm cron. A second model added without the same build-time fetch quietly restores the original problem while looking like a pure feature addition.
