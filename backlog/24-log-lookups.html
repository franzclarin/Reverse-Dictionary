Keep what people searched for

✓ Done P2 · instrumentation
In plain terms

Today — the app answered a search and then forgot it completely. The only thing it wrote down was a shadow-log row holding a fingerprint of the question — a hash, not the words — plus the single best answer. That was a deliberate choice, and it held for the app's entire history.

Done — every real search now stores the description exactly as typed, together with every word it returned and each word's score, in ranked order.

Why it matters — this improves search by nothing at all. What it buys is the ability to eventually ask a question the project has never been able to ask: do people phrase things the way the test set assumes? Every score in this repo rests on 312 questions one person wrote in one sitting.

Followed by RD-25 — this shipped double-counting

Everything below describes one row per request, and that is what shipped. It was wrong by one word: the site was sending every search twice, so every query wrote two rows. The cause was older than this ticket — an effect with no cleanup, which React's development mode double-invokes on purpose — and it had been costing two lookups per search for months without leaving a trace. This log is what made it visible.

RD-25 corrects it to one row per search, with a searchId and a unique index. Nothing else here changes.

Status: done 2026-08-31 — table live in Neon, rows verified end-to-end Touches: new QueryLog model + migration, new lib/queryLog.ts, ~12 lines in app/api/lookup/route.ts Does not touch: retrieval — lib/glossSearch.ts, lib/embedder.ts, the frozen set and every committed run are unchanged Risk carried: a stated invariant was retired, and it was load-bearing in five documents

The change is one table and a dozen lines. Most of the work was that the property it removes was quoted as a reason in five separate places.

What actually changed

“No query text has ever been logged” was not an accident of a small app. It was a design property, enforced by lib/shadowLookup.ts hashing the query before storing it, and it is cited by name in CLAUDE.md (twice), README.md, ARCHITECTURE.md, and four tickets — as the reason the eval set is hand-authored (RD-10, RD-14, RD-09, RD-02). Retiring it without amending those would have left the repo confidently, quietly wrong.

What is stored

One row per non-debug request to /api/lookup:

columnwhat it holds, and why
queryThe description as typed — untrimmed, uncased. The route already caps it at 500 characters.
kHow many results were asked for. Not decoration: the results page re-runs the same query with a larger k when “Load more” is clicked, so repeated rows with identical text are expected, and k is what explains them.
results[{ word, similarity }, …] in rank order, as jsonb. The same array the client receives, so the log and the answer cannot disagree. Stored as one value rather than two parallel arrays precisely so the words and their scores cannot drift out of step.
timingMsEmbed + pgvector time, matching the number the page shows. Excludes the log write itself, which would otherwise make the log a measurement of the log.

Three decisions worth the space

The write is awaited, not fire-and-forget

runShadowLookup is fire-and-forget, and correctly so: it samples 10% of traffic and an occasional lost row costs an agreement rate nothing. A log meant to be complete cannot take that trade. On Vercel, an unawaited promise races the function being frozen after the response — and Next 14.2 has neither after() nor waitUntil, so there is no correct way to defer it. So it is awaited, and wrapped: a failure prints [lookup] query log failed (non-fatal) and the search still returns 200 with its results. That was tested by forcing the insert to fail, not assumed.

The cost is honest and worth stating: ~100 ms from a laptop, which is a full extra round trip to Neon on top of a query that already costs 800–3,000 ms from here. In production both the function and the database sit in iad1, where a single insert is a fraction of that — the same distinction CLAUDE.md already draws about the eval harness's dbMs. Measured, not modelled: with logging off, the same requests cost ~12–30 ms over db ok ms; with it on, ~110–125 ms.

/explain's requests are excluded

The /explain page calls the same endpoint with debug: true. Those are someone poking at a demonstration, not someone trying to find a word, and counting them would quietly change what the table means. This is the same reasoning the shadow log already applies, written out in the same place.

The rows are unlabelled, and that bounds everything they can say

A logged query carries no correct answer. It can characterise phrasing, length, and which words get returned; it can never say whether the answer was right. This is lib/shadowLookup.ts's “agreement is not accuracy” argument applied to a richer log, and it is the reason RD-10's Stack Exchange harvest is still the measurement to build. Those threads arrive with the answer attached. This table does not, and no amount of it ever will.

Prerequisite knowledge

Why this is not the same as RD-10

It is tempting to read this ticket as “RD-10, but from our own traffic.” It is not, for two independent reasons. The rows are unlabelled, as above. And this app has too little traffic to accumulate a set from — which is the exact deadlock RD-02's shadow gate died of, retired at n ≈ 2 rather than satisfied. Building a plan on “wait for the log to fill” would be that same mistake wearing a new costume.

The frozen set is untouched, and stays untouched

eval/sets/v1.jsonl is frozen and every recorded run predates the first logged query, so nothing on the results tables moves. The blind-authoring rule that produced it was a response to the leakage risk of a model fine-tuned on 181,149 WordNet glosses — that risk is unchanged, and a future set drawn from real phrasing would be a new file with a new sha256, never an edit to this one.

Learnings

!

A one-table change falsified five documents. “No query text has ever been logged” was quoted in CLAUDE.md twice, README.md, ARCHITECTURE.md and four tickets, and in most of them it was not a fact being reported but a reason being given — for why the eval set is hand-authored, for why RD-09's training pairs must be synthesised. Half this ticket's work was in the prose. Same shape as the stale 512 MB ceiling RD-17 corrected: a claim nobody re-checks is worse than one nobody wrote down.

✓

The right cost to pay was latency, not completeness. Copying the shadow log's fire-and-forget pattern would have looked consistent and produced a log with silent, unknowable holes in it — the worst property a record can have, because you cannot tell a quiet day from a dropped write. The two logs answer different questions and correctly make opposite trades.

✓

Storing the array the client received, rather than rebuilding it, is what makes the log evidence. The row holds the exact object returned. There is no second serialisation to drift — the same discipline that keeps scripts/lib/retrieval.ts mirroring the route instead of reimplementing it.

!

Having the data is not having the measurement. The seductive misreading of this table is that it makes RD-10 unnecessary. It does the opposite: unlabelled rows can raise the question of whether the test set's phrasing is representative and can never answer it, so the labelled harvest is still the work.

Acceptance criteria

  • QueryLog created in Neon with a createdAt index; results is jsonb
  • A real search writes one row, with rank order and scores intact
  • “Load more” writes a second row with the larger k, not a duplicate to be deduped away
  • /explain's debug: true requests write no row
  • A failing log write returns 200 with results and one non-fatal log line — forced and observed, not assumed
  • Added latency measured with logging on and off, and reported rather than absorbed
  • Retrieval untouched: npm run verify-viz passes, the serving SELECT still byte-identical
  • Every document quoting “no query text has ever been logged” amended with the date and what the rows do and do not license
