Generate query-style training pairs from glosses

P2 · training data
In plain terms

Write training examples that sound like real people, because the existing ones sound like a dictionary.

Today — the model has only ever seen terse definitions as its input examples. Nobody types "a motor vehicle with four wheels" into a search box.

Do — use a language model, offline, to write 5–10 natural phrasings for each meaning — "the thing you drive", "when you...", "something that..." — as new training material.

Why it matters — this is the raw material RD-09 needs. Two cautions carried in the ticket: the examples must be attached to meanings rather than bare words, or it retrains the exact fault RD-02 removed; and it runs as an offline script, so the live app gains no AI dependency.

Depends on: RD-12 reporting first — it addresses a much larger slice of the same problem Feeds: RD-09 (the retrain), RD-15 (negatives are mined against these queries) Touches: a new dev-only script in scripts/, a new corpus file. No application code and no runtime dependency. Risk: contaminating eval/sets/v1.jsonl; teaching the model an LLM's register rather than a person's Est: days for the pipeline, then a metered generation run

RD-09 step 2 already names this — "a target word paired with several ways a person might actually describe it" — and leaves it entirely unspecified. This ticket is that specification. The training corpus is 181,149 WordNet triplets whose queries are terse gloss text; the app is used with sentences like "when you can't remember a word." Nothing in training has ever looked like that.

Read the size of this bet before starting

Retraining competes for the 23.0% of queries where the target is never retrieved at all, at any depth to 100. The other 53.0% — already retrieved, merely mis-ranked — belongs to RD-12, which needs no new data and no training run. The prior on retraining in this codebase is also weak: the last attempt bought +4.5pp, below the project's own 6pp bar. This ticket is worth doing; it is not worth doing first.

Task

  1. Pair queries with synsets, not words. The obvious framing — (synthetic_query, word) — retrains the exact defect RD-02 was built to remove. CLAUDE.md's measurement is unambiguous: VocabEmbedding stores bare-lemma vectors, cos(embed(word), stored[word]) = 1.000000, and search was "a 12-word description against a 1-token document." Generate from the gloss and key the pair to the synset, matching what the index actually holds since the cutover.
  2. Dev-only script, no runtime dependency. Same posture as tsx and wordnet-db: a devDependency, never imported by the app, API key read from the environment, output written as JSONL and committed. The deployed bundle keeps its no-generative-dependency invariant — Claude was removed on 2026-08-18 and nothing here reintroduces it into a request path.
  3. Meter the cost before committing to it. 117,791 synsets × 5–10 queries is 0.6–1.2M generations. Run a stratified pilot first — sampled across POS and across meta.zipf frequency bands, since eval/data/zipf-en.tsv already provides the banding — sized to what one RD-09 eval cycle can actually consume. A full-corpus run before a pilot has demonstrated the pairs help is spending the budget on an untested assumption.
  4. Verify disjointness from every eval set, mechanically. Output must be checked against eval/sets/v1.jsonl (sha256 cc03e134…) and, once it exists, RD-10's v2-elu.jsonl. Check on both query and target, and record the check in the corpus provenance. This is the one step that cannot be skipped and re-added later.
  5. Vary the phrasing deliberately, and record the templates. "when you…", "something that…", "the word for…" are three registers, not one; generating all pairs under a single instruction produces a corpus that teaches one sentence shape. Store the prompt/template with each row so the corpus can be sliced by register at eval time — the same discipline meta.style already gives the eval harness.
  6. Record full provenance: generating model and version, prompt templates, generation date, sampling strategy, and the disjointness check. Every run in this project records its config; a training corpus that cannot say how it was made cannot be reproduced or audited later.

Prerequisite knowledge

The known failure mode is style, not quality

Synthetic queries measure a model's idea of how people ask, not how people ask. RD-10 rejected generative text for evaluation on exactly this ground, and that judgement stands — which is why the honest held-out check for any model trained on this corpus is RD-10's set, not this one. Training on synthetic data and evaluating on synthetic data would produce a number that only describes the generator.

The training/eval distinction is why this is allowed at all

RD-10's objection was scoped to eval data, where a generated query would replace the real-phrasing signal the set exists to provide. Training is a different use: the corpus is a means of teaching the encoder a register, and it is measured against sets it did not write. State this distinction in the corpus README so a later reader does not see it as a contradiction of RD-10.

ELU data must stay out of this corpus

RD-10 flags that Stack Exchange content is CC-BY-SA and that SE's terms carry restrictions around AI training use — a different question from evaluation use. RD-10 names this ticket's predecessor as "the ticket most tempted to reach for it." Do not use ELU rows as training pairs unless that is separately cleared, and keep the two corpora physically separate so the mistake requires an explicit act.

There is no real-query corpus to compare against, by design

No query text has ever been logged. lib/shadowLookup.ts stores a hash and top-1 only; the pre-RD-06 Lookup model was {id, userId, createdAt}, a rate-limit counter. There is nothing to validate the synthetic register against except RD-10's harvested set, which is a further argument for doing RD-10 first.

Learnings

!

The natural framing of this ticket contains the bug RD-02 just fixed. "Generate queries for each vocab word" produces word-keyed pairs, which is the lemma-target shape that cost this project 13.9 points of recall. The index changed at the cutover; anything downstream that still thinks in words rather than synsets is describing the old system.

✓

A held-out split is free and was the original run's real gap. RD-09 records this already: the first fine-tune ran eval_on_start: False and prediction_loss_only: True, which is why its 10.9% figure is unusable. More data does not fix that; only a split does. This corpus should be generated with its split boundary decided up front, not carved out afterwards.

Acceptance criteria

  • Pairs keyed to synsets and generated from gloss text, not to bare lemmas
  • Generator is a dev-only script in scripts/; no new runtime dependency and no key required to build or serve the app
  • Stratified pilot run and evaluated before any full-corpus generation is funded
  • Disjointness from eval/sets/v1.jsonl (and v2-elu.jsonl if present) mechanically verified and recorded
  • v1.jsonl verified byte-identical afterward
  • Prompt templates stored per row so the corpus can be sliced by register
  • Provenance recorded: model, templates, date, sampling strategy, disjointness result
  • No Stack Exchange / ELU content present in the corpus
  • Train/held-out boundary decided and documented before generation, not after
