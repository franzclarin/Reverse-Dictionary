Resolve critical/high vulnerabilities without breaking the pinned embedder

P1 · dependency security
In plain terms

A security warning in a library the app cannot casually upgrade.

Today — the automated security scanner reports 3 critical and 17 high-severity problems. All of them are inside the dependency chain of the one package that loads the search model.

Do — fix the warnings without changing what the model does.

Why it matters — the obvious fix — upgrade everything — risks silently changing the numbers the model produces, which would change search results with no visible sign that anything happened. No known way to exploit these in this app; this is about not carrying known-broken code.

Touches: package.json, @xenova/transformers Risk: a naive fix breaks production search Est: ~half day investigation, more if a real upgrade is needed

npm audit reports 3 critical and 17 high severity findings, all inside the dependency tree of the one package this app cannot casually change: @xenova/transformers. The path of least resistance — npm audit fix --force — silently downgrades it to 1.4.2, which is a different major version than the one this app's entire query/document vector space was built against. This ticket is about finding a fix that doesn't do that.

Size — M, uncertain
1 package.json edit, if overrides work
Best case is a two-line overrides block plus a regression check. Worst case — if onnxruntime-web hard-pins an incompatible protobufjs range — is an open-ended investigation into a major-version upgrade path. Size the second path only after the first is actually tried.
Impact — medium, risk not recall
3 critical / 17 high findings addressed
No known exploited path given this app's usage (server-side, fixed inputs, no user-supplied protobuf/image data reaching these libraries). Impact is compliance/security posture and reducing background npm audit noise — not retrieval quality, and not user-visible if done right.

Task

  1. Confirm the finding is still current: npm audit (re-run — versions may have moved since this ticket was written).
  2. Try dependency overrides first, not a parent-package downgrade. In package.json: 
    "overrides": {
  "protobufjs": "^8.7.2",
  "sharp": "^0.35.0"
}
    This pins the vulnerable transitive dependencies to patched versions while leaving @xenova/transformers@^2.17.2 untouched. It may fail if onnxruntime-web has a hard version constraint incompatible with protobufjs 8.x's API — check for that before assuming it'll just work.
  3. After any dependency change, run the representation probe: does cos(embed(word), stored_vector[word]) ≈ 1.0 still hold for a sample of known words? This is the exact test scripts/probe-representation.ts already does — if it doesn't confirm identity, the override broke something in the ONNX pipeline (tokenization, pooling, or the runtime itself) and must not ship regardless of what the audit report says.
  4. Run npm run eval and diff the output against the committed eval/runs/baseline.json — this is a much stronger check than the probe alone, since it exercises the full query path, not just self-similarity.
  5. If overrides don't resolve cleanly: research whether a newer @xenova/transformers major (there's since been a rename/successor line — check current npm state, this ticket was written against 2.17.2) fixes the chain natively, and whether its API is compatible with this app's exact { quantized: false }, { pooling: "mean", normalize: true } usage in lib/embedder.ts. Do not attempt this without the eval harness as a regression gate — a subtly different pooling default would degrade recall silently, not throw an error.
  6. If no fix exists that preserves representation identity: document the residual risk explicitly (what's exploitable, under what conditions, given this app's actual usage — server-side, fixed inputs, no user-supplied protobuf/image data reaching these libraries directly) rather than leaving it as an unexplained "known audit finding."

Prerequisite knowledge

The vulnerable chain

Both vulnerable packages have patched upstream releases — the problem is only that @xenova/transformers@2.x pins old ranges of each

Why "just run the suggested fix" is the wrong move here

npm audit fix --force's only offered resolution is installing @xenova/transformers@1.4.2. This app's lib/embedder.ts depends on very specific, deliberately-chosen behavior from the 2.x line ({ quantized: false } loading onnx/model.onnx, mean pooling + normalize matching the pipeline that seeded VocabEmbedding's 141,854 stored vectors). A major downgrade is not guaranteed to preserve that pipeline's exact numerical output, and there is no reason to assume it does without testing — a silently different vector space would degrade every search result without throwing a single error.

Learnings

✓

This app already has the exact regression test this fix needs. scripts/probe-representation.ts (self-similarity) and npm run eval (full retrieval quality) were both built for a different purpose — validating the embedder against known-good behavior — but they're precisely what a dependency-upgrade risk assessment needs too. No new tooling required here.

!

Not investigated previously — flagged, not resolved. An earlier audit pass explicitly deferred this ("17 high/3 critical — not investigated, out of scope for this migration audit"). This ticket exists because that deferral needs to be closed out deliberately, not left open indefinitely as background noise in every future npm install.

Acceptance criteria

  • npm audit critical/high count reduced, or a written justification for what remains and why it's acceptable given this app's actual attack surface
  • Representation probe still passes: known words' embeddings still match their stored VocabEmbedding vectors
  • npm run eval output matches the committed baseline within noise
  • Decision and rationale recorded somewhere durable (this ticket, or a CLAUDE.md note) — not just a green CI badge with no explanation
