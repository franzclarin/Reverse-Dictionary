Retrain on better training data — a second attempt, with an eval split this time

P3 · sentence embeddings
In plain terms

Teach the model better, rather than changing what it searches.

Today — the model learned from 181,149 terse dictionary definitions. Real users type sentences like "when you can't remember a word", which look nothing like that.

Do — retrain it on better material — with a proper held-out split this time, so the result can actually be trusted.

Why it matters — this competes for the 23% of searches where the right answer is never found at all. The other 53% — found but ranked too low — belongs to RD-12, which needs no retraining. The last attempt at this bought only +4.5 points, so the ordering matters.

Depends on: RD-02's cutover being measured and decided first — done 2026-08-27 Sourcing steps: RD-14 (query-style pairs), RD-15 (hard negatives) Compare against: RD-12, which addresses a slice more than twice this one's size without retraining Touches: the training pipeline in reverse_dict_model.zip (gitignored, not in this repo's tracked code), eval/ Risk: large effort for an unproven payoff; easy to repeat the original run's own methodological mistake Est: weeks, not days — data sourcing + a full retrain + eval cycle

The obvious next lever for "make search better" is more/better training data for the fine-tune. It's a real idea and worth capturing — but the project has already measured what the first attempt at this bought, and the honest number is small. This ticket exists so the idea isn't lost, not because the evidence currently favors it over what's already queued.

Size — L
Data sourcing + full retrain + eval cycle
Unlike RD-02 (a flag flip against code that already exists), there is no shortcut here: new training pairs have to be sourced or authored, a training run has to happen outside this repo, and the result has to go through the full eval harness before it means anything.
Impact — uncertain
Prior attempt: +4.5pp lenient R@1, a null result
Fine-tuned vs. base model, same index, is only +4.5pp — below the project's own pre-committed 6pp bar for calling an effect real (p=0.029 despite that). Swapping what's indexed (RD-02, zero retraining) bought +12.9–15.7pp instead. Retraining is not the proven lever in this codebase; indexing is.
How much is left for retraining to win — measured 2026-08-27

Recomputed from eval/runs/prod_gloss_shipped.json at depth 100, the live gloss index splits its failures cleanly. The target is at rank 1 for 24.0% of authored reachable queries, sits at ranks 2–100 for a further 53.0%, and is never retrieved at all for 23.0%. Only that last slice is a retrieval problem — the middle one is a ranking problem, which RD-12 addresses with no new data and no training run.

This bounds the ticket. Retraining competes for 23 points with a prior of +4.5pp from the last attempt; reranking competes for 53 with none of the sourcing cost. That does not make this ticket wrong — a better representation is the only thing that reaches the 23% — but it settles the ordering, and it is evidence that did not exist when this ticket was written.

⚠ Core bet tested by proxy and lost — RD-16, 2026-08-28. Read before starting.

This ticket's bet is that a better training corpus, on the same model, buys recall. That experiment already exists as a public checkpoint. multi-qa-MiniLM-L6-cos-v1 is the same architecture, same width, same layer count as franzclarin/ReverseDictionary, pretrained on 215 million question–answer pairs against this project's 181,149 WordNet triplets. Capacity held fixed, corpus changed — precisely the ablation this ticket proposes.

It scored 18.5% lenient R@1 against the fine-tune's 25.4%: −7.0 points, 35 regressions against 15 wins, p = 0.007. The only significant result in a six-cell sweep, and it points the wrong way.

Two more of this ticket's assumptions went with it. The register gap that motivates its step 2 is +1.8pp on the live index (RD-14). And enriching the indexed text with WordNet's usage examples — the "the glosses are too thin" reading — cost 1.4 points and raised echo.

What this does and does not establish. It does not prove no corpus could help; a corpus built for description-to-definition paraphrase is not what any of these checkpoints was trained on. It does establish that the largest, most obvious, most professionally-built alternative corpus makes this task worse, which is a much harder starting position than this ticket assumed. And it converges with RD-12: QA and web-passage training data hurt here at both the bi-encoder and the cross-encoder stage, for the same reason.

Status: held, not cancelled. The 23.0% never-retrieved slice is still only reachable by a better representation. But the prior on getting one by retraining is now measured and negative, and the next move on this path is RD-10 — a ruler that can resolve a bet this expensive. Full write-up: eval/METHODS.md §14.

Task

  1. RD-02 has landed (2026-08-27: lenient R@1 10.1% → 24.0%, echo 40.7% → 14.5%), so this ticket's original blocker is cleared. It is replaced by a new one: let RD-12 report first. Same reasoning, larger margin — RD-12 is cheaper, needs no data sourcing, and addresses 53 points against this ticket's 23.
  2. Source additional training pairs. Two directions, not mutually exclusive:
    • More sense-level (gloss, lemma) triplets — the existing corpus already has 181,149 of these and only bought +4.5pp, so more of the same shape has a weak prior for moving the needle further.
    • Natural-language query-style pairs — a target word paired with several ways a person might actually describe it, closer to how the app is really used than WordNet's terse gloss text. No real user query text has ever been logged (the shadow log stores a hash + top-1 only, by design — see lib/shadowLookup.ts), so these pairs have to be synthesized or authored, not mined from production. RD-14 is the specification of this step, including the correction that the pairs must be keyed to synsets rather than bare lemmas — word-keyed pairs would retrain the exact defect RD-02 removed. RD-15 covers the negatives, with its own correction about which metric they actually move.
  3. Hold out a genuine evaluation split this time. The original run used eval_on_start: False and prediction_loss_only: True — no held-out split at all, which is exactly why its own training-time recall figure (10.9%) is unusable and must not be cited. A second attempt that repeats this mistake will produce another number nobody can trust. Note also that "hold out real user query logs" is not available — none exist, by design; RD-10's harvested set is the substitute, and it is the honest check on a model trained on RD-14's synthetic register precisely because nobody in this project wrote it.
  4. Keep any new eval data strictly disjoint from eval/sets/v1.jsonl and its authoring process. v1's entire value rests on being blind to every gloss and never regenerated in place — if training data or a held-out split leaks into it, every downstream recall number in this project stops meaning what it currently means.
  5. Evaluate the retrained model through the existing harness, not a one-off script — run it against both index shapes (lemma and gloss), the way Phase E's 2×2 design already separates representation from indexing. Assuming a new fine-tune's gain stacks on top of RD-02's gloss-index gain is an assumption, not a result, until measured.
  6. Compare against cell_gloss_ft_synset (25.8% lenient R@1, the current best cell) using the harness's paired McNemar comparison, same as every other result in this project. An isolated new recall number is not evidence on its own — see CLAUDE.md's own repeated caveat about n≈300 comparisons. If RD-12/RD-13 have shipped by then, the production baseline to beat is the reranked path, not prod_gloss_shipped.

Prerequisite knowledge

  • The fine-tune has already been shown to be the weaker lever, not the stronger one. CLAUDE.md §"Headline results": lemma_base → lemma_ft is +4.5pp (null, below threshold) while lemma_ft → gloss_ft is +12.9pp (real, p < 0.0001). Don't let "we should retrain" quietly outrank "we should finish shipping the index swap" — they are not the same size of bet.
  • The original training run's number is not a baseline to beat — it's unusable. No held-out split means 10.9% describes memorization, not retrieval. A new run needs its own honestly-measured baseline via the eval harness, not a comparison against that figure.
  • There is no corpus of real user queries anywhere in this system, by design. RD-06 removed the last thing that could have logged them, and the shadow log (RD-01/RD-02) deliberately stores only a hash and top-1 word, never query text — a privacy invariant, not an oversight. Any "natural language query" training data has to be authored or synthesized from scratch, the same way eval/sets/v1.jsonl was.

Learnings

!

This ticket is speculative on purpose. It's here because the idea is legitimate and shouldn't be lost, not because the evidence currently in this repo argues for prioritizing it. If a future session picks this up, re-read CLAUDE.md's "Headline results" table first — the numbers may have shifted once RD-02's live decision and soak data are in.

✓

"Add more training data" and "add a held-out split" are two different fixes, and the second one is free. The original run's biggest methodological gap wasn't data volume, it was having no way to tell if the model generalized at all. Any retrain that skips a held-out split repeats the same mistake regardless of how much new data goes in.

Acceptance criteria

  • RD-02's cutover decision recorded before this ticket starts — done: cut over, 2026-08-27
  • RD-12's reranker result recorded before this ticket starts, so the two are prioritised against measured numbers
  • New training pairs sourced and documented, distinct in kind from the original 181,149 WordNet triplets (RD-14), keyed to synsets rather than bare lemmas
  • Hard negatives, if used, mined per RD-15 and evaluated on lenient R@1 as well as strict
  • Training run includes a genuine held-out split (eval_on_start enabled, not prediction_loss_only-only)
  • Held-out/training data verified disjoint from eval/sets/v1.jsonl
  • New model evaluated via scripts/eval.ts against both lemma and gloss index cells, paired McNemar vs. cell_gloss_ft_synset
  • Decision recorded (adopt / hold) with headline numbers, following CLAUDE.md's "Headline results" convention
