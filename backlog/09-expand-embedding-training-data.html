Retrain on better training data — a second attempt, with an eval split this time

P2 · sentence embeddings
Depends on: RD-02's cutover being measured and decided first Touches: the training pipeline in reverse_dict_model.zip (gitignored, not in this repo's tracked code), eval/ Risk: large effort for an unproven payoff; easy to repeat the original run's own methodological mistake Est: weeks, not days — data sourcing + a full retrain + eval cycle

The obvious next lever for "make search better" is more/better training data for the fine-tune. It's a real idea and worth capturing — but the project has already measured what the first attempt at this bought, and the honest number is small. This ticket exists so the idea isn't lost, not because the evidence currently favors it over what's already queued.

Size — L
Data sourcing + full retrain + eval cycle
Unlike RD-02 (a flag flip against code that already exists), there is no shortcut here: new training pairs have to be sourced or authored, a training run has to happen outside this repo, and the result has to go through the full eval harness before it means anything.
Impact — uncertain
Prior attempt: +4.5pp lenient R@1, a null result
Fine-tuned vs. base model, same index, is only +4.5pp — below the project's own pre-committed 6pp bar for calling an effect real (p=0.029 despite that). Swapping what's indexed (RD-02, zero retraining) bought +12.9–15.7pp instead. Retraining is not the proven lever in this codebase; indexing is.

Task

  1. Don't start before RD-02 is decided. RD-02 is the cheaper, already-measured, much larger win. Let it land and get a real production readout before spending weeks competing with it for the same "improve search" goal.
  2. Source additional training pairs. Two directions, not mutually exclusive:
    • More sense-level (gloss, lemma) triplets — the existing corpus already has 181,149 of these and only bought +4.5pp, so more of the same shape has a weak prior for moving the needle further.
    • Natural-language query-style pairs — a target word paired with several ways a person might actually describe it, closer to how the app is really used than WordNet's terse gloss text. No real user query text has ever been logged (the shadow log stores a hash + top-1 only, by design — see lib/shadowLookup.ts), so these pairs have to be synthesized or authored, not mined from production.
  3. Hold out a genuine evaluation split this time. The original run used eval_on_start: False and prediction_loss_only: True — no held-out split at all, which is exactly why its own training-time recall figure (10.9%) is unusable and must not be cited. A second attempt that repeats this mistake will produce another number nobody can trust.
  4. Keep any new eval data strictly disjoint from eval/sets/v1.jsonl and its authoring process. v1's entire value rests on being blind to every gloss and never regenerated in place — if training data or a held-out split leaks into it, every downstream recall number in this project stops meaning what it currently means.
  5. Evaluate the retrained model through the existing harness, not a one-off script — run it against both index shapes (lemma and gloss), the way Phase E's 2×2 design already separates representation from indexing. Assuming a new fine-tune's gain stacks on top of RD-02's gloss-index gain is an assumption, not a result, until measured.
  6. Compare against cell_gloss_ft_synset (25.8% lenient R@1, the current best cell) using the harness's paired McNemar comparison, same as every other result in this project. An isolated new recall number is not evidence on its own — see CLAUDE.md's own repeated caveat about n≈300 comparisons.

Prerequisite knowledge

  • The fine-tune has already been shown to be the weaker lever, not the stronger one. CLAUDE.md §"Headline results": lemma_base → lemma_ft is +4.5pp (null, below threshold) while lemma_ft → gloss_ft is +12.9pp (real, p < 0.0001). Don't let "we should retrain" quietly outrank "we should finish shipping the index swap" — they are not the same size of bet.
  • The original training run's number is not a baseline to beat — it's unusable. No held-out split means 10.9% describes memorization, not retrieval. A new run needs its own honestly-measured baseline via the eval harness, not a comparison against that figure.
  • There is no corpus of real user queries anywhere in this system, by design. RD-06 removed the last thing that could have logged them, and the shadow log (RD-01/RD-02) deliberately stores only a hash and top-1 word, never query text — a privacy invariant, not an oversight. Any "natural language query" training data has to be authored or synthesized from scratch, the same way eval/sets/v1.jsonl was.

Learnings

!

This ticket is speculative on purpose. It's here because the idea is legitimate and shouldn't be lost, not because the evidence currently in this repo argues for prioritizing it. If a future session picks this up, re-read CLAUDE.md's "Headline results" table first — the numbers may have shifted once RD-02's live decision and soak data are in.

✓

"Add more training data" and "add a held-out split" are two different fixes, and the second one is free. The original run's biggest methodological gap wasn't data volume, it was having no way to tell if the model generalized at all. Any retrain that skips a held-out split repeats the same mistake regardless of how much new data goes in.

Acceptance criteria

  • RD-02's cutover decision (cut over / hold / iterate) recorded before this ticket starts
  • New training pairs sourced and documented, distinct in kind from the original 181,149 WordNet triplets
  • Training run includes a genuine held-out split (eval_on_start enabled, not prediction_loss_only-only)
  • Held-out/training data verified disjoint from eval/sets/v1.jsonl
  • New model evaluated via scripts/eval.ts against both lemma and gloss index cells, paired McNemar vs. cell_gloss_ft_synset
  • Decision recorded (adopt / hold) with headline numbers, following CLAUDE.md's "Headline results" convention
