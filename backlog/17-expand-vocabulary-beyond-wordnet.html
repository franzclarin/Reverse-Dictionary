Expand the vocabulary beyond WordNet 3.0

✓ Done · 2026-08-28
In plain terms

The app can return petrichor now. It could not before, and not because it ranked it badly — it had never heard of it.

Was — every word the app could return came from a dictionary frozen in 2006. petrichor, selfie, umami, hangry, gaslighting and deepfake were simply not in it.

Did — added a filtered slice of Wiktionary: 575,534 meanings over 443,645 words, taking the index from 118k to 693k. Built it as a throwaway copy first and scored it there, so nothing touched the real database until the numbers existed.

Result — on the 287 questions the app could already answer, no change (−0.3pp, 23 better and 22 worse, p = 1.00) — but first-page recall rose 54% → 60%. On the 25 it could never answer, 0% → 32% answered correctly first, and 20 of 25 now appear somewhere in the results at all.

The surprise — the cautious version of this change was much worse than doing nothing. Adding only words the old dictionary lacked lost 8.4 points, with 24 questions made worse and not one made better. Adding everything, including second definitions of words already covered, cost nothing. See the learnings.

Shipped: 2026-08-28 — GlossEmbedding 117,791 → 693,325 rows Added: scripts/lib/wiktionary.ts (the filter), lib/oewn.ts, build-supplement{,-cell,-index}.ts, verify-supplement-cell.ts, three probes Also fixed: a live 404 bug — 8,005 words search could return had no word page Write-up: eval/METHODS.md §15

Search answers out of GlossEmbedding — 117,791 synsets, expanding to 149,400 distinct answerable lemmas. That table is built by scripts/build-gloss-index.ts from wordnet-db, which is Princeton WordNet 3.0, frozen in 2006. A word that is not a lemma in one of those synsets cannot be returned by any query, at any probes setting, under any reranking scheme. This is the one failure mode in this project that is not a ranking problem.

The evidence was already in the repo

eval/sets/v1.jsonl carries 25 rows marked meta.reachable: false, excluded from every headline number — and petrichor is literally one of them. The full list, verified against the live index on 2026-08-28:

hangry · limerence · saudade · sonder · staycation · vaporware · veganism · cryptocurrency · deepfake · fatberg · microplastic · petrichor · philtrum · selfie · clickbait · crowdfunding · webinar · capsize · corpsing · doomscrolling · enshittification · gaslighting · greenwashing · loiter · mansplaining

That is 25 of 312 authored rows — 8.0% of the benchmark scoring zero by construction, and it has been sitting there since the set was frozen on 2026-08-19. It is the largest single named failure class in the repo that nobody has costed.

Found while writing this ticket — two of the 25 are no longer unreachable

capsize and loiter are in the live index. The reachable flags were computed against VocabEmbedding (141,854 rows); RD-02's gloss index was built straight from WordNet and carries 149,400 lemmas, repairing part of the old ~5% coverage gap as a side effect nobody was looking for. The real figure is 23 rows, 7.4%.

meta.reachable is stored truth inside a frozen set, so this is not an edit — it is either a v2 or an analysis-time recompute. RD-05 already owns that job and its rule ("new version, never in-place").

What was done

  1. Confirmed the cap, and it was wrong by four orders of magnitude. SHOW neon.max_cluster_size is 16 TB, not 512 MB; the database was at 673 MB. CLAUDE.md is corrected. Both of this ticket's storage levers — converting VocabEmbedding to halfvec, or dropping it — existed only to buy room that was never scarce, so neither was done.
  2. Tried Open English WordNet first. It is not the ticket. 120,630 synsets and 152,286 lemmas, +5,307 / −1,003 against WordNet 3.0, and it covers 2 of the 23 targets. It also re-keys every synset, which would orphan every recorded run. Measured, recorded, not adopted — npm run probe:oewn.
  3. Built the filter as code, in two arms. scripts/lib/wiktionary.ts, one exported rule per predicate and a kill count for each, all recorded in the committed eval/data/supplement-manifest.json. Two refusals are load-bearing: no frequency gate (the committed Zipf table contains none of the words this ticket exists to add) and no register gate (slang, informal and Internet are exactly where hangry and doomscrolling live).
  4. Built it as a local copy, not a table. Both arms were composed onto RD-16's verified cell by copying its numbers byte for byte and appending, so any measured difference is the new rows and nothing else — checked by byte-comparing the shared half rather than assuming it. No database write until the numbers existed.
  5. Scored two slices on a fixed denominator. The regression test on the 287 questions both indexes can answer; the coverage slice on the 25 they cannot, reported on its own. The harness now scores that slice rather than counting it — a count cannot tell "indexed" from "indexed and findable".
  6. Migrated, on a gate fixed before the runs. Insert only: the 117,791 WordNet rows are untouched, so rollback is one DELETE ... LIKE 'wikt:%'. The vectors come out of the copy that was measured rather than being re-encoded, because a re-encode is a second embedding path in disguise.
  7. Fixed the word pages, which were already broken. See below — this was not a hypothetical about future words.

Found en route — 8,005 words search could return had no page

getWordData() decided whether /word/<slug> was real by asking VocabEmbedding — the rollback table, which search stopped using at the RD-02 cutover. The two tables disagreed on 8,005 lemmas, so search happily returned capsize and /word/capsize returned 404 — and this ticket's own expansion took that gap to 379,633, so it could not have shipped without the fix. Existence is now decided by the index search actually queries, backed by a new GIN index on lemmas; neighbours still come from the lemma table, so no page that worked before behaves differently.

And a second, quieter one: 47 of the 475 rows in Word are Claude-era profiles with no vector in either table — petrichor was one, with a real definition and no index entry. Asking Postgres for neighbours of a word it has no vector for is not an error: the subquery is NULL, every distance is NULL, and the page rendered twelve arbitrary words presented as semantic neighbours. A word with no vector has no neighbours, and the code now says so.

There is also no similarity floor anywhere in app/api/lookup/route.ts. A missing word does not fail loudly — it returns the nearest wrong thing with a plausible-looking score, which is why this class of failure has stayed invisible.

The headline metric punishes success here. Fix the denominator before running anything.

This is the trap in the ticket, and it is not obvious. Headline recall is computed over the 287 reachable rows: prod_gloss_shipped gets rank 1 on 69 of them, 69/287 = 24.0%. Add the missing vocabulary and those 23 rows become reachable and enter the slice. If the new words are indexed but never rank first:

staterank-1 hitsslicelenient R@1
today6928724.0%
vocabulary added, new words never rank first6931022.3%
vocabulary added, new words rank first half the time8031025.8%

A strictly better app can score 1.7 points worse. Report this comparison on a fixed denominator — the 287 rows both systems can answer — and carry the coverage slice as its own separate number, exactly the way echo is carried beside recall rather than folded into it. Anything else makes the decision on an artefact of arithmetic.

At 1.85 KB per synset: an unfiltered million-sense Wiktionary index is ~1.85 GB, which is not a plan. A hard filter landing at 300–500k senses is ~555–925 MB on top of the existing 673 MB. Two levers if that does not fit:

  • Convert VocabEmbedding to halfvec — frees ~225 MB, costs nothing. It is still vector(384) at 4 bytes per dimension while the gloss table is already halved. CLAUDE.md records halfvec(384) as measured-free: 0 discordant pairs, mean cosine 0.99999998. This is the cheapest 225 MB in the repo and is worth doing whether or not this ticket proceeds.
  • Drop VocabEmbedding entirely — frees 451 MB, costs two things. It backs getRelatedWords() on every word page, and it is RD-02's rollback path. Step 7 above removes the first dependency; the second is a judgement call about how settled the cutover is.

The obvious filter does not work — checked, so it does not have to be checked again

Gating Wiktionary by word frequency using the already-committed eval/data/zipf-en.tsv (92,937 rows) looks like the way to keep the list small and useful. It is not. That table is OpenSubtitles-derived, and it contains none of petrichor, sonder, hangry, umami, saudade, doomscrolling, gaslighting or limerence. A frequency filter removes precisely the words this ticket exists to add. CLAUDE.md already warns that this source "under-weights literary/technical vocabulary" — this is that warning arriving with a bill.

The risk this ticket has to clear

Going from 117,791 candidates to several hundred thousand can only make discrimination harder for the queries that already work — the encoder's job gets strictly worse as the field gets more crowded, and RD-16 established that this encoder is already failing to discriminate finely among 117,791 glosses. Wiktionary also carries far more near-duplicate and obsolete senses than WordNet, which is the worst possible shape of distractor.

This project has twice now measured a confident premise and found it wrong — RD-12's reranker and RD-16's corpus bet. Step 4 exists so that this one is measured in a local file at zero production exposure, exactly as those were.

Learnings

!

The cautious version of a change can be the destructive one, and it was not close. Adding only words the dictionary lacked lost 8.4 points with 24 questions made worse and zero made better — a shape that means pure loss, not a trade. The reason is visible once stated: on a question WordNet can already answer, a row for a word WordNet lacks can only ever be a wrong answer. That arm is a clean measurement of what distractors cost. The permissive arm adds the same distractors plus second definitions of words already covered, and those are extra chances for the right answer — which is what paid for them. Do not model added candidates as pure distractors. That intuition is what made the losing arm look like the safe one, and it was written into this ticket's own risk section before anything was measured.

✓

A 2006 lexicographer's gloss is often worse at being found than a plain modern one. The wins are not obscure words — they are vertigo, marrow, funnel, navigator, pungent, haggle, pillow. In every case WordNet's definition lost and Wiktionary's won for the same word. pungent went from rank 91 to rank 1. Coverage was the stated goal; a second, plainer phrasing of things already covered turned out to matter just as much.

!

Documentation that is wrong and conservative is worse than documentation that is missing. The storage ceiling was recorded as 512 MB against a live 16 TB, and against 673 MB of actual usage — so the file said the database was over a limit it was nowhere near. Two of this ticket's planned mitigations existed solely to reclaim space that was never scarce. A missing number sends you to run the query; a confidently wrong one does not.

✓

The metric trap this ticket warned about did not exist, and checking cost five minutes. The fear was that fixing coverage would grow the denominator and make a better app score worse. It cannot: the reachable flag is stored inside a frozen set, so the 287-row slice is the same 287 rows before and after. The warning describes a denominator that moves with the index — worth writing down, and worth verifying against the actual harness rather than fixing a problem that was already prevented.

!

A key scheme that is merely untidy in a test file is silent data loss in a table. Numbering senses within an entry produced 5,925 colliding keys, because Wiktionary splits homographs into one entry per etymology — cat the animal, cat the Unix command, cat the drug. In the local copy that is harmless. Through ON CONFLICT DO UPDATE the second row overwrites the first, and the shipped table would have been 5,925 rows short of the one the numbers describe, with nothing to indicate it. The builder now refuses to write a colliding key.

✓

Copy the half you are not testing. Both arms reuse the WordNet vectors byte for byte instead of recomputing them, and a check compares the bytes. Re-encoding would have been an hour spent proving the model is deterministic — and if it had come out microscopically different, every difference in the score would have been unattributable after the fact. It also caught nothing, which is the point: the check is what turns "it must be the same" into "it is".

✓

Coverage buys candidacy, not rank, and the honest report says so. 20 of 25 previously impossible questions now retrieve the right answer somewhere; only 8 put it first. doomscrolling, gaslighting and hangry are in the index and still outside the top 100. Those were coverage failures and are now ranking failures — real progress, and a different problem, not a solved one.

!

Two tables, one question, and nobody noticed for a month. RD-02 moved search to the gloss index and left the word pages asking the old table whether a word exists. The sets differed by 8,005 words, so search returned words whose pages 404'd — a user-visible bug that no metric in this repo measures, because every metric here scores retrieval and none of them opens a page. When a system switches which store is authoritative, the thing to grep for is not the query that moved, but every other reader of the store it left.
