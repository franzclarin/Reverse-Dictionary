Expand the vocabulary beyond WordNet 3.0

P1 · data engineering
In plain terms

The app cannot return petrichor. Not because it ranks it badly — because it has never heard of it.

Today — every word the app can return comes from a dictionary frozen in 2006. petrichor, selfie, umami, hangry, gaslighting and deepfake are simply not in it.

Do — add a modern word source, most likely Wiktionary, and measure two things: whether the new words can actually be found, and whether adding them damages the words that already work.

Why it matters — this is the only remaining idea in the backlog that adds a capability rather than improving a ranking. It is also the only one whose mechanism is not in doubt: if the word is in the index it can be retrieved, and if it is not, nothing else in this repo can help.

Depends on: nothing — but reads better after RD-10, which would say which missing words people ask for Touches: scripts/build-gloss-index.ts, a new source reader beside scripts/lib/wordnet.ts, GlossEmbedding, a new eval slice Risk: ~1M new candidates make ranking harder for the 92% that already work — and the headline metric punishes success here (see below) Est: 2–4 days, plus a one-off embedding run measured in hours

Search answers out of GlossEmbedding — 117,791 synsets, expanding to 149,400 distinct answerable lemmas. That table is built by scripts/build-gloss-index.ts from wordnet-db, which is Princeton WordNet 3.0, frozen in 2006. A word that is not a lemma in one of those synsets cannot be returned by any query, at any probes setting, under any reranking scheme. This is the one failure mode in this project that is not a ranking problem.

The evidence was already in the repo

eval/sets/v1.jsonl carries 25 rows marked meta.reachable: false, excluded from every headline number — and petrichor is literally one of them. The full list, verified against the live index on 2026-08-28:

hangry · limerence · saudade · sonder · staycation · vaporware · veganism · cryptocurrency · deepfake · fatberg · microplastic · petrichor · philtrum · selfie · clickbait · crowdfunding · webinar · capsize · corpsing · doomscrolling · enshittification · gaslighting · greenwashing · loiter · mansplaining

That is 25 of 312 authored rows — 8.0% of the benchmark scoring zero by construction, and it has been sitting there since the set was frozen on 2026-08-19. It is the largest single named failure class in the repo that nobody has costed.

Found while writing this ticket — two of the 25 are no longer unreachable

capsize and loiter are in the live index. The reachable flags were computed against VocabEmbedding (141,854 rows); RD-02's gloss index was built straight from WordNet and carries 149,400 lemmas, repairing part of the old ~5% coverage gap as a side effect nobody was looking for. The real figure is 23 rows, 7.4%.

meta.reachable is stored truth inside a frozen set, so this is not an edit — it is either a v2 or an analysis-time recompute. RD-05 already owns that job and its rule ("new version, never in-place").

Size — M/L
A filter, an embedding run, and a migration
The pipeline is mostly built: build-gloss-index.ts already groups senses, embeds with the production embedder and batch-inserts. What is new is a second source reader and — the actual work — the filter deciding which of Wiktionary's roughly one million English senses are worth indexing.
Impact — high, and bounded
7.4% of authored queries currently score zero
Unlike RD-09/RD-14/RD-15 the mechanism is not in doubt. Unlike RD-12 there is no model that has to cooperate. The uncertainty is entirely on the cost side — storage, licensing, and what a million extra distractors do to the queries that already work.

Task

  1. Confirm the actual Neon cap first. Everything below is sized against it, and nobody currently knows what it is. RD-01's plan changed mid-flight — the plan was upgraded, the DROP INDEX was skipped, the database sits at 673MB — and that ticket explicitly records the new cap as not verified. CLAUDE.md still says 512MB and ~460MB, so anyone sizing this ticket from it sizes it against a ceiling that is both wrong and lower than reality.
  2. Try the cheap source before the expensive one. Open English WordNet is the maintained successor to PWN 3.0 with the same synset/gloss structure, so adopting it changes only the reader inside scripts/lib/wordnet.ts and costs roughly zero extra storage. Diff its lemma set against the live 149,400 and look for the petrichor class specifically. If it is there, that is the entire ticket. Expect it is not — but this is an afternoon, and step 3 is a week.
  3. Build the candidate set from Wiktionary. The machine-readable extractions (Kaikki.org / wiktextract) publish per-sense glosses as JSONL, which maps directly onto a GlossEmbedding row. Filter hard — English only, real gloss text, drop inflected forms, proper nouns, and obsolete/rare-tagged senses. Commit the filter as code, not as a description. It determines both the storage bill and the distractor count, and it is the parameter this ticket will be re-run against.
  4. Build it as a local cell, not a table. scripts/build-encoder-cell.ts already produces full-scale cells outside Postgres under EVAL_CELL_DIR, and RD-16's cells cross-validated against a live production run to the digit. Zero database writes, no migration, no rollback path needed to reach a decision. Do not touch GlossEmbedding until the numbers exist.
  5. Score two slices, and report both. (a) the 287-row reachable slice, paired McNemar against prod_gloss_shipped — this is the regression test, and adding candidates can only make it harder; (b) the 23 still-unreachable rows as a new coverage slice, whose queries are already written blind and already frozen. Thin at n=23, which is RD-10's argument, not a reason to skip it.
  6. Decide the migration separately. If the numbers hold, size the table, pick the storage lever (below), and treat the insert as its own RD-01-shaped job with its own audit.
  7. Decide what a new word's page shows. getRelatedWords() reads VocabEmbedding, which any newly added word will not be in — so /word/petrichor would resolve to a page with an empty definition and no related words. Deriving neighbours from GlossEmbedding instead is the obvious fix and is a behaviour change worth measuring on its own.

There is also no similarity floor anywhere in app/api/lookup/route.ts. A missing word does not fail loudly — it returns the nearest wrong thing with a plausible-looking score, which is why this class of failure has stayed invisible.

The headline metric punishes success here. Fix the denominator before running anything.

This is the trap in the ticket, and it is not obvious. Headline recall is computed over the 287 reachable rows: prod_gloss_shipped gets rank 1 on 69 of them, 69/287 = 24.0%. Add the missing vocabulary and those 23 rows become reachable and enter the slice. If the new words are indexed but never rank first:

staterank-1 hitsslicelenient R@1
today6928724.0%
vocabulary added, new words never rank first6931022.3%
vocabulary added, new words rank first half the time8031025.8%

A strictly better app can score 1.7 points worse. Report this comparison on a fixed denominator — the 287 rows both systems can answer — and carry the coverage slice as its own separate number, exactly the way echo is carried beside recall rather than folded into it. Anything else makes the decision on an artefact of arithmetic.

At 1.85 KB per synset: an unfiltered million-sense Wiktionary index is ~1.85 GB, which is not a plan. A hard filter landing at 300–500k senses is ~555–925 MB on top of the existing 673 MB. Two levers if that does not fit:

  • Convert VocabEmbedding to halfvec — frees ~225 MB, costs nothing. It is still vector(384) at 4 bytes per dimension while the gloss table is already halved. CLAUDE.md records halfvec(384) as measured-free: 0 discordant pairs, mean cosine 0.99999998. This is the cheapest 225 MB in the repo and is worth doing whether or not this ticket proceeds.
  • Drop VocabEmbedding entirely — frees 451 MB, costs two things. It backs getRelatedWords() on every word page, and it is RD-02's rollback path. Step 7 above removes the first dependency; the second is a judgement call about how settled the cutover is.

The obvious filter does not work — checked, so it does not have to be checked again

Gating Wiktionary by word frequency using the already-committed eval/data/zipf-en.tsv (92,937 rows) looks like the way to keep the list small and useful. It is not. That table is OpenSubtitles-derived, and it contains none of petrichor, sonder, hangry, umami, saudade, doomscrolling, gaslighting or limerence. A frequency filter removes precisely the words this ticket exists to add. CLAUDE.md already warns that this source "under-weights literary/technical vocabulary" — this is that warning arriving with a bill.

The risk this ticket has to clear

Going from 117,791 candidates to several hundred thousand can only make discrimination harder for the queries that already work — the encoder's job gets strictly worse as the field gets more crowded, and RD-16 established that this encoder is already failing to discriminate finely among 117,791 glosses. Wiktionary also carries far more near-duplicate and obsolete senses than WordNet, which is the worst possible shape of distractor.

This project has twice now measured a confident premise and found it wrong — RD-12's reranker and RD-16's corpus bet. Step 4 exists so that this one is measured in a local file at zero production exposure, exactly as those were.

Learnings

!

A coverage hole is invisible to the metric built to catch it. Excluding unreachable rows from headline recall is the right call — including them would depress every number by a constant and compare nothing. The side effect is that 8% of the benchmark scores zero forever and no number on the dashboard ever moves, so the largest named failure class in the repo sat in the file from the day it was frozen without ever being costed. Track the size of an excluded slice as its own number, or exclusion quietly becomes deletion.

✓

RD-02 expanded the vocabulary and nobody noticed. It was argued, measured and shipped as a ranking fix. It also took the answerable lemma set from 141,854 to 149,400, because the gloss index was built from WordNet directly rather than from the accidentally-curated VocabEmbedding table — which is why capsize and loiter are still flagged unreachable while working fine. A change can improve something the frozen instrument is not pointed at, and freezing the instrument is what hides it.

!

An improvement can move the headline number down. Fixing coverage grows the denominator faster than the numerator unless the new words rank well immediately. Any metric whose denominator is "the questions we can currently answer" silently penalises answering more questions. Fix the denominator before running the comparison, not after reading a result you dislike.

!

CLAUDE.md's storage section is stale in the direction that matters. It records a 512MB cap and ~460MB of usage against a live 673MB on an upgraded plan — and RD-01's own ticket says so. Documentation that is wrong and conservative is worse than documentation that is merely missing: it produces a confident "this cannot fit" from someone who never runs the query.

Acceptance criteria

  • The upgraded Neon cap confirmed and written down, and CLAUDE.md's storage figures corrected against the live database
  • Open English WordNet's lemma delta against the live 149,400 measured and recorded, whatever the verdict
  • Source filter committed as code, with the resulting sense count and projected table size recorded
  • Expanded index built as a local cell under EVAL_CELL_DIR and verified by synset before any database write
  • Regression measured on a fixed 287-row denominator, paired McNemar against prod_gloss_shipped; echo reported beside it as usual
  • Coverage slice scored separately over the 23 unreachable rows and reported as its own number, never folded into headline recall
  • Licence obligations recorded in the index's provenance if a share-alike source ships
  • Word-page behaviour for a newly added word decided and implemented, not discovered by a user
  • eval/sets/v1.jsonl verified byte-identical throughout; any reachable correction lands as a new version
