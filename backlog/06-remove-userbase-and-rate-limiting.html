Remove the userbase (Clerk auth, credits, saved words, leaderboard) and rate limiting entirely

P1 · product simplification ✓ Done · 2026-08-26
In plain terms

The app had user accounts that nobody used. They are gone.

Was — sign-in and sign-up, saved word collections, a credits and streak system, an unused leaderboard, and per-user request throttling — none of it serving any purpose.

Did — removed all of it: 3 routes, 5 components, 4 database tables and 3 outside services.

Result — done 2026-08-26. Search is now anonymous and unthrottled, and about 15 files got simpler. Every call site was checked by hand before deleting rather than assumed — the lesson RD-04 had already recorded.

Supersedes: RD-04 (its full scope, not just the already-dead games code) Touches: Clerk, Upstash, User/SavedWord/Lookup/GameRound, /api/lookup Risk: irreversible schema drop; production data loss for saved words/credits Est: ~2–3 hrs

The app shipped a full Clerk-auth-backed userbase — sign-in/up, saved-word collections, a credits/streak system, and an unused leaderboard — plus Upstash-Redis rate limiting on /api/lookup. None of it is required for the app's actual purpose (semantic word search), and RD-04 had already found dead games code hanging off the same credits system. Rather than trim the dead branches, this ticket removes the whole tree: auth, the userbase tables, and rate limiting, leaving search as a fully anonymous, unthrottled feature.

Size — M
3 whole routes, 5 components, 4 Prisma models, 3 deps deleted
Mechanical removal across ~15 files plus a schema migration. No new logic written — every call site was verified by grep before deleting, not inferred from commit messages (the lesson RD-04 already learned the hard way).
Impact — simplification
Zero retrieval-quality change, smaller attack/maintenance surface
Doesn't touch VocabEmbedding/GlossEmbedding/ShadowLookup or the search path itself — those have no relation to any userbase table. The win is fewer moving parts: no Clerk keys, no Upstash credentials, no "fail open" rate-limit edge cases to reason about.

Prerequisite knowledge

What's actually load-bearing vs. dead, verified by grep

All three branches are auth-gated by the same middleware — removing the middleware makes every one of them dead, so they come out together rather than piecemeal

Why this supersedes RD-04 instead of running alongside it

RD-04 explicitly scoped itself to the already-orphaned games plumbing and said "this isn't delete the whole credits feature" — at the time, credits/saved-words/leaderboard were still considered live product surface. This ticket changes that decision: the whole feature is going, not just its dead branches. Every file RD-04 named is deleted here too (lib/gameTokens.ts, lib/gameUtils.ts, and the three dead lib/credits.ts functions), plus everything RD-04 deliberately kept.

Schema removal order

SavedWord.wordId is the only foreign key from the userbase side into real word data (Word.savedBy). VocabEmbedding, GlossEmbedding, and ShadowLookup — the actual search infrastructure — have zero relation to User/SavedWord/Lookup/GameRound, so the migration only ever touches the four userbase tables plus one relation field on Word.

Learnings

✓

The leaderboard API had no caller. app/api/leaderboard/route.ts existed and worked, but grep found zero UI referencing it anywhere in app/ or components/ — it was already dead weight before this ticket, just not caught by RD-04 because RD-04 didn't look past the games-specific functions.

✓

The rate-limit Subsystem branch was already unreachable. checkRateLimit() always fails open — it never throws SubsystemError("ratelimit", …) — so SUBSYSTEM_MESSAGES.ratelimit in the old /api/lookup route was dead code even before this removal. One less thing to explain to a future reader once "ratelimit" comes out of the Subsystem union too.

!

Dropping User/SavedWord/Lookup/GameRound is a destructive migration. This repo has no separate local database — .env.local's DATABASE_URL points straight at the shared Neon instance — so the migration was written by hand and applied only after explicit confirmation, via prisma db execute --file per CLAUDE.md's migration gotcha (Neon's pooled connection breaks migrate deploy's advisory lock). Ran clean; verified via a direct table listing that the four tables are gone and Word/VocabEmbedding/GlossEmbedding/ShadowLookup are untouched.

✓

Found and fixed pre-existing migration-history drift while here. prisma migrate status showed the two most recent prior migrations (add_gloss_embeddings, add_shadow_lookup) as "not yet applied" even though their tables demonstrably existed with data — they'd been run via db execute --file (the same Neon workaround this ticket used) without ever being recorded in _prisma_migrations. Backfilled with prisma migrate resolve --applied so migrate status now reads clean.
